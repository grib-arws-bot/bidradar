## 03. BidRadar도 n8n으로 해야 하는가 — **결론: 사용하지 않음** ✅

> **결정 (2026-08-31, Jeffrey)** — BidRadar는 n8n을 사용하지 않는다. 수집·처리 전 구간을 코드로 구현한다.

n8n 인프라가 이미 운영 중이므로 진지하게 따진 결과입니다. 판단 근거를 남깁니다.

### 왜 ARWS에서는 맞았고 BidRadar에서는 아닌가

| | ARWS 수집기 | BidRadar 수집기 |
|---|---|---|
| 성격 | **고정 파이프라인** | **설정을 해석하는 런타임** |
| 구조 | GitHub 수집·Flow 수집·Figma 수집이 각각 정해진 형태 | 소스가 DB 레코드. 어댑터 타입·필드 매핑을 읽어 매번 다르게 동작 |
| n8n 적합도 | **높음** — 정확히 이걸 위한 도구 | **낮음** — 워크플로우가 "목록 조회 → 루프 → 타입 분기 → 매핑 적용"이 되는 순간, n8n은 *느리고 디버깅 어려운 Python*이 됨 |

**이 구분이 결론의 뼈대입니다.** n8n이 나쁜 도구여서가 아니라, BidRadar의 수집기가 n8n이 잘하는 형태가 아니기 때문입니다.

### 찬성 논거 (약하지 않음)

- 인프라가 **이미 돌아감** — compose·백업·터널·2단 배포 파이프라인 완비
- 학습 비용 **0** — 이미 17개 워크플로우를 만든 경험
- 실행 이력·시각적 디버깅이 **공짜로** 따라옴
- 새 소스 추가를 "워크플로우 복제"로 처리 가능 (설계안 04절의 저비용 대안)

### 반대 논거 — 결정적인 것부터

**(0) SSRF 방어를 n8n에서는 만들 수 없음 ← 사실상 여기서 결론이 남**
n8n HTTP Request 노드는 주어진 URL을 그대로 호출합니다. 리졸브된 IP 대역 검증, 리다이렉트 홉마다 재검증, DNS 고정(rebinding 차단)을 하려면 Code 노드에서 fetch를 직접 구현해야 하고, 그러면 n8n을 쓰는 의미가 사라집니다. **관리자가 임의 URL을 입력하는 시스템에서 이건 타협 불가 항목**입니다(설계안 04-4).

**(1) 버전 관리가 사실상 불가능**
워크플로우 JSON이 232KB·128KB·100KB. `git diff`가 의미를 잃고, 코드 리뷰도 머지도 불가능합니다. 커밋 429건 중 워크플로우 변경분은 리뷰된 적이 없다고 봐야 합니다.

**(2) "같은 패턴을 손으로 복제하다 하나를 빠뜨린다"가 반복 패턴**
의사결정 로그에서 확인된 실제 사례:

| 항목 | 내용 |
|---|---|
| #66 후속 | `localhost:8080 → baserow` 치환이 **파일 하나에만 누락**. 200행을 넘긴 적이 없어 몇 주간 잠복하다 노출 |
| #202 | n8n 워크플로우 **UTF-8 손상 전수조사** → 실제 버그 1건 발견 |
| #113 | prod 발행상태 보존 정책 + Flow수집 무응답 버그 |
| — | 하위 경로가 워크플로우 JSON에 박혀 있어 "바꾸면 여러 개를 직접 수정해야 함" |

> 이건 **코드였으면 공용 함수 하나로 끝날 문제**입니다. n8n에서는 노드를 복제할 때마다 같은 실수가 재생산됩니다.

**(3) 설계안 04절의 핵심 요구를 n8n으로는 충족 불가**
BidRadar의 차별점은 **관리자가 화면에서 소스를 추가**하는 것입니다. n8n은 *개발자가 워크플로우를 만드는 도구*이지, *최종 사용자가 데이터 소스를 등록하는 런타임*이 아닙니다. 이 요구를 유지하려면 소스 레지스트리는 코드여야 합니다.

**(4) Baserow는 이 데이터에 안 맞음**
S3 기관 프로파일·S4 시장 분석은 3년치 시계열 집계·낙찰 업체 점유율 같은 쿼리를 돌립니다. Baserow REST 페이지네이션으로 이걸 하면 ARWS에서 이미 겪은 `fetchAllRowsMeta`/`fetchPageBatch`류 우회 코드를 다시 짜게 됩니다(server.js 1334~1460줄이 실제로 그 코드입니다).

### 확정된 구성

| 영역 | 선택 | 근거 |
|---|---|---|
| 수집·매핑·스코어링·소스 레지스트리 | **Python 코드** | 위 (0)(1)(2)(3) |
| 데이터 저장 | **새 PostgreSQL** | 위 (4) |
| 스케줄 | **cron / APScheduler** (수집 코드와 같은 프로세스) | n8n을 트리거로만 쓰면 중간 계층만 늘어남. 실패 처리·재시도가 코드 안에 있는 편이 자연스러움 |
| 인프라 (compose·배포·백업·터널) | **ARWS `infra/` 패턴 복제** | ★ 가장 큰 재사용 이득 |
| n8n | **v1에서 사용하지 않음** | 아래 |

**n8n을 다시 꺼낼 수 있는 자리 — v1 범위 밖, 출력 쪽에서만**

- **알림 발송** — ARWS에 이미 수신자 필터·발송 로그까지 갖춘 이메일 워크플로우가 있음. BidRadar가 나중에 메일/Flow 알림을 붙일 때는 재사용 가치가 실재함
- **ARWS 연동** — BidRadar 결과를 일일보고에 밀어 넣는 접착제

이 둘은 **지금 설계에 넣지 않습니다.** 필요해지는 시점에 판단합니다.

### 운영 부담도 계산에 넣었음

BidRadar 워크플로우를 같은 인스턴스에 얹으면 17개가 30개가 됩니다. 결정로그에 이미 **#2649 "컨테이너 혼동 주의"**(`infra-n8n-1` vs `n8n`)와 **#113 "prod 발행상태 보존 정책"** 항목이 있는데, 이 관리 부담이 두 시스템분으로 늘어납니다. 별도 인스턴스를 띄우면 "이미 있어서 좋다"는 이점 자체가 사라집니다.

### 판단 기준 (다음 결정에도 재사용)

> **이 로직이 앞으로 계속 바뀌고, 바뀔 때 diff를 봐야 하는가?**
> → 그렇다 = 코드 · 아니다 = n8n

BidRadar 수집(소스 추가·매핑 변경·스코어링 튜닝)은 전부 "그렇다"입니다. "매일 아침 9시에 메일 발송"은 "아니다"입니다.

## 06. 스택 권고 수정 ⚠️

**앞선 대화에서 저는 HTMX를 권했습니다. ARWS를 보고 그 판단을 수정합니다.**

제 논거는 "React는 이 규모에 무겁다"였는데, 그건 **처음부터 짜는 경우**에 성립합니다. 실제로는:

- Minimal MUI 템플릿(`@minimal/material-kit-react`) 기반의 **작동하는 관리자 UI 130파일**이 이미 있음
- MUI DataGrid·ApexCharts가 이미 붙어 있음 — BidRadar의 S1 목록·S4 차트에 그대로 대응
- React 19 / Vite 6 / TS 최신 구성, ESLint·Prettier 정비 완료
- 무엇보다 **본인이 이걸로 한 번 완주했음**

**수정된 선택지 비교**

| | A안 · FastAPI + HTMX | B안 · ARWS 패턴 복제 (React+MUI + Python 백엔드) |
|---|---|---|
| 기존 자산 재사용 | 없음 | **높음** — 템플릿·컴포넌트·배포 설정 |
| 학습 비용 | 반나절 (HTMX) | 0 |
| Claude Code 세션 효율 | 높음 (파일 수 적음, 빌드 없음) | 중간 (프론트/백 왕복) |
| 프로세스 수 | 1 | 2 (+nginx) |
| 향후 SaaS 전환 | 프론트 재작성 필요 | **이미 SPA** |
| 위험 | 인력 수급, 소수파 | **ARWS의 구조 문제 반복** |

**권고: B안으로 기울어집니다. 단, 조건부입니다.**

ARWS의 실패는 **React 때문이 아니라 CLAUDE.md 부재 때문**입니다. 같은 스택으로 가되 아래 세 가지를 1일차에 박으면, ARWS보다 나은 결과가 나옵니다.

1. **CLAUDE.md** — "라우터는 얇게, 로직은 `services/`" + "파일 500줄 넘으면 분리" 명시
2. **백엔드는 Python(FastAPI)** — Express 아님. 수집기의 비동기 I/O와 복잡한 집계 쿼리 때문
3. **테스트를 완료 조건에 포함** — 구현스펙 10절의 작업 단위별 완료 조건을 그대로 사용

> 단, A안도 여전히 유효합니다. "이번엔 프론트 빌드 없이 가볍게 가보고 싶다"가 목적이라면 A안이 맞습니다. **자산 재사용 vs 단순함**의 선택이며, 기술적 우열이 아닙니다.

## 07. 일정 재산정

구현스펙은 "백엔드 1명 × 8~10주 + 프론트 0.5명 × 4주"로 잡았습니다. **ARWS 실측 속도를 보면 보수적입니다.**
