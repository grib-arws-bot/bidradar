## 1. 확정 — 시스템 이름 BidRadar (2026-08-31)

**결정** 영문명 `BidRadar`, 국문 병기 시 "입찰 레이더". 약어는 만들지 않음.

**근거**
- `PBR`(Public Bidding Radar) 후보를 검토했으나 **한국 비즈니스 맥락에서 PBR은 주가순자산비율(Price-to-Book Ratio)의 표준 약어**. 임원 보고·사업계획서에서 오독이 확실시됨. 그래픽 업계의 Physically Based Rendering과도 충돌
- 영어권 공공조달 표준 용어는 *procurement* / *tender*이고 *bidding*은 경매 뉘앙스를 겸함. 다만 사내 도구이며 국문 "입찰"과 1:1로 대응되는 점을 우선함
- 두 단어라 약어가 불필요하고, 사내에서 "레이더 봤어?"처럼 자연스럽게 쓰임
- 저장소 디렉터리 `BidRadar/`, User-Agent `GribBidRadar/1.0`과 일치

**보류** 외부 판매(SaaS) 전환 시에는 도메인 확보·상표 검색을 포함한 별도 네이밍이 필요. 그 경우에도 사내 코드네임은 BidRadar 유지.

## 2. 확정 — n8n 미사용 (2026-08-31)

**결정** BidRadar는 n8n을 사용하지 않는다. 수집·매핑·스코어링·소스 레지스트리 전 구간을 Python 코드로 구현하고, 스케줄은 cron 또는 APScheduler를 수집 코드와 같은 프로세스에서 운용한다.

**배경** ARWS가 n8n + Baserow 기반으로 성공적으로 운영 중이고 인프라(compose·백업·터널·2단 배포)가 이미 갖춰져 있어, 재사용 가능성을 진지하게 검토함.

**근거 (결정적인 순서)**

1. **SSRF 방어를 n8n에서 구현할 수 없음** — n8n HTTP Request 노드는 주어진 URL을 그대로 호출한다. 리졸브 IP 대역 검증·리다이렉트 홉마다 재검증·DNS 고정을 하려면 Code 노드에서 fetch를 직접 짜야 하고, 그 시점에 n8n을 쓰는 의미가 사라진다. **관리자가 임의 URL을 입력하는 시스템에서 이건 타협 불가 항목**(설계안 04-4)
2. **관리자 소스 등록(설계안 04절)이 n8n으로는 구현 불가** — n8n은 개발자가 워크플로우를 만드는 도구지, 최종 사용자가 데이터 소스를 등록하는 런타임이 아니다
3. **수집기의 성격이 다름** — ARWS 수집기는 *고정 파이프라인*(GitHub/Flow/Figma 각각 정해진 형태)이라 n8n에 잘 맞았다. BidRadar 수집기는 *설정을 해석하는 런타임*(소스가 DB 레코드, 어댑터 타입·필드 매핑을 읽어 동작)이라, n8n으로 만들면 "느리고 디버깅 어려운 Python"이 된다
4. **버전 관리 불가** — ARWS 워크플로우 JSON이 232KB·128KB. `git diff`가 의미를 잃고 코드 리뷰·머지가 안 된다. ARWS 결정로그 #66 후속(`localhost:8080→baserow` 치환이 파일 하나에만 누락되어 몇 주 잠복), #202(UTF-8 손상 전수조사)가 그 비용의 실례
5. **Baserow도 부적합** — S3 기관 프로파일·S4 시장 분석은 3년치 시계열 집계와 낙찰 업체 점유율 쿼리가 필요. Baserow REST 페이지네이션으로 하면 ARWS `server.js` 1334~1460줄의 `fetchAllRowsMeta`/`fetchPageBatch`류 우회 코드를 다시 짜게 된다
6. **운영 부담** — 같은 인스턴스에 얹으면 워크플로우가 17개→30개. ARWS 결정로그 #2649(컨테이너 혼동 주의)·#113(prod 발행상태 보존 정책)의 관리 부담이 두 시스템분으로 늘어난다. 별도 인스턴스를 띄우면 "이미 있어서 좋다"는 이점 자체가 소멸

**검토 중 정정한 것** 초기에는 "스케줄 트리거만 n8n"을 제안했으나 철회. n8n이 HTTP로 앱을 깨우고 앱이 실제 일을 하는 구조는 중간 계층만 늘리며, 실패 처리·재시도가 코드 안에 있는 편이 자연스럽다.

**다시 꺼낼 수 있는 자리 (v1 범위 밖)**
- 알림 발송 — ARWS에 수신자 필터·발송 로그를 갖춘 이메일 워크플로우가 이미 있음
- ARWS 연동 — BidRadar 결과를 일일보고에 밀어넣는 접착제

**재사용하는 것** n8n이 아니라 **`infra/`** — docker-compose 구조, GitHub Actions 2단 배포, 백업 스크립트, Cloudflare Tunnel. 여기엔 논쟁의 여지가 없음.

**앞으로 재사용할 판단 기준**
> 이 로직이 앞으로 계속 바뀌고, 바뀔 때 diff를 봐야 하는가? → 그렇다 = 코드 / 아니다 = n8n

## 3. 확정 — 프론트 우선 기획, 백엔드를 거기 맞춤 (2026-08-31)

**결정** 화면과 사용자 흐름을 먼저 확정하고, 화면이 요구하는 데이터를 역산해 API 계약 → DB 스키마 → 수집기 필드 순으로 정의한다.

**근거**
- 사용자 가치가 먼저 검증됨. 안 쓰는 API·컬럼을 만들 확률이 낮아짐
- **프론트 스택 결정(HTMX vs React+MUI)을 뒤로 미룰 수 있음** — 화면 기획이 끝나야 "이 화면들이 실제로 얼마나 인터랙티브한가"를 보고 스택을 정할 수 있다. 순서상 이게 맞다

**주의 — 기획 순서와 구현 순서는 다름**
화면에서 역산되지 않는 영역이 둘 있다.
- `security/url_guard.py`(SSRF 방어) — 화면 요구와 무관하게 존재해야 하며, 구현 순서에서는 여전히 **가장 먼저**(구현스펙 U1)
- 소스 레지스트리 데이터 모델 — 화면(S5)이 힌트를 주지만, 어댑터 추상화는 수집 요구에서 나온다

따라서 **기획은 프론트 우선, 구현은 U1(SSRF) → 기반 → 화면** 순서를 유지한다.

## 4. 확정 — 프론트 스택: React + MUI (2026-08-31)

**결정** Vite + React 19 + MUI 7 (ARWS `admin-page-v2`의 Minimal 템플릿 패턴 복제) + FastAPI(Python) 백엔드.

**검토했던 대안 (A안)** FastAPI + Jinja2 + HTMX + Alpine + Tailwind — 단일 프로세스, 빌드 없음, 파일 수가 적어 Claude Code 세션 효율이 높음. 기존 자산 재사용은 없음.

**초기 권고와 그 철회 (기록용)**
처음에는 A안(HTMX)을 권고했음. 논거는 "이 앱의 상호작용은 목록·필터·폼·상세뿐이라 HTMX의 스윗스팟"이었으나, **요구사항이 구체화되면서 그 전제가 무너짐**:

1. **이미 HTMX 때문에 타협한 설계가 2건** — S2 칸반 드래그앤드롭을 드롭다운으로 대체, S5 등록 마법사 5단계 상태를 hidden input으로 유지. 착수 전에 이미 2건이면 "3건 이상이면 전환 신호"라는 자체 기준에 근접
2. **S7 관심 주제 화면 추가가 결정적** — 프리셋 토글 + 태그 칩 추가/삭제 + 금액 슬라이더 + **저장 전 실시간 미리보기**는 클라이언트 상태 중심 폼. 서버 왕복으로 미리보기를 갱신하면 반응이 굼뜨고, hidden input과 부분 템플릿이 지저분하게 늘어남
3. **시각 품질** — MUI DataGrid·Autocomplete·DatePicker·Chip·Skeleton은 손으로 만들면 확실히 품질이 떨어짐. 특히 DataGrid. "Tailwind로 그릴 수 있다"와 "이미 있다"는 다름
4. **ApexCharts 이미 설치·검증됨** — S4 시장 분석의 차트 4종에 그대로 대응

**감수하는 대가** 프로세스 2개 + nginx / API 계약 이중 관리 / Claude Code 세션에서 프론트↔백 왕복 / ARWS의 단일 `server.js` 3,659줄 문제 반복 위험.

**마지막 항목에 대한 방어** ARWS의 실패 원인은 React가 아니라 **CLAUDE.md 부재**였음. 스택과 무관하게 아래는 확정:
- CLAUDE.md를 **첫 커밋에** 배치
- `app/services/` 분리를 1일차부터 강제
- **파일 500줄 상한**을 CLAUDE.md에 명시
- 각 작업 단위 완료 조건에 테스트 포함

**백엔드는 Express가 아니라 FastAPI(Python)** — 수집기의 비동기 I/O(여러 기관 API 동시 호출)와 S3·S4의 복잡한 집계 쿼리 때문. ARWS의 Express는 Baserow/n8n 프록시 역할이었으나 BidRadar 백엔드는 수집·처리 본체임.

**프로토타입에 미치는 영향** 화면 프로토타입은 **MUI 룩앤필로 작성**한다. 정적 HTML이지만 MUI의 색·타이포·컴포넌트 형태(Card·Chip·Tabs·DataGrid)를 따라 그리면 컴포넌트 매핑이 거의 1:1로 떨어져, 프로토타입이 기획서이자 마크업 명세가 됨.

## 6. 확정 — 배포 구성: stg=개발 PC, prod=서버, 빌드는 PC에서만 (2026-08-31)

**결정** ARWS와 동일한 2단 배포 구조를 복제한다.

| 환경 | 위치 | 역할 |
|---|---|---|
| **stg** | 개발 PC (self-hosted runner) | 빌드 + 로컬 기동 + 육안 확인 |
| **prod** | 서버 | 빌드 없이 **완성된 이미지만 받아서** 교체 |

**핵심 제약** 프로덕션 서버 사양이 작아 서버에서 직접 빌드하면 안 됨. ARWS에서 서버가 응답불가까지 간 실사고가 있음(ARWS 결정로그 #96 → #98·#99에서 로컬 빌드로 전환). **BidRadar도 처음부터 이 제약을 전제로 설계한다.**

**배포 흐름 (ARWS `deploy-to-production.ps1` 패턴)**

```
0) 사전점검 — 로컬 HEAD == origin/main, 워킹트리 clean 아니면 즉시 중단
1) 로컬 PC에서 이미지 빌드 (무거운 작업은 여기서만)
2) 사람이 stg 화면 육안 확인
3) 이미지에 git 커밋 해시 태그 부여 (롤백용, latest와 별도 보관)
4) docker save → tar.gz → scp 로 서버 전송
5) 서버 git 체크아웃을 origin/main으로 ff  ← 이미지에 안 담기는 설정(compose 등) 반영
6) 로컬 .env vs prod .env 변수 차이 경고 (prod .env는 수동 관리)
7) 서버: 현재 이미지를 :previous 로 백업 → docker load → docker compose up -d (--build 없이)
8) 로컬 임시파일 정리
9) prod 응답 확인 + 로그인 스모크 테스트 (HTTP 200뿐 아니라 실제 로그인까지)
```

**GitHub Actions 2단 분리** `deploy-stg.yml` / `deploy-prod.yml` 모두 `workflow_dispatch`만. 자동 트리거 없음 — private 저장소에서 Required reviewers를 못 쓰므로 **"사람이 버튼을 눌러야 prod로 넘어간다"**를 워크플로우 분리로 대체.

**ARWS에서 이미 값을 치른 안전장치 — 그대로 가져올 것**

| 항목 | 내용 |
|---|---|
| main 브랜치 가드 | `workflow_dispatch`는 임의 브랜치 지정이 가능. self-hosted 러너에 실 시크릿이 있으므로 **체크아웃 전에** ref가 main인지 확인해 아니면 즉시 실패 |
| `.env` 정리 | 러너가 `_work`를 재사용하므로 복사한 실 `.env`가 남음 → `if: always()`로 마지막에 삭제 |
| `Assert-Success` | PowerShell `$ErrorActionPreference="Stop"`은 docker/ssh/scp/git의 비정상 종료코드를 못 잡음 → 네이티브 명령마다 `$LASTEXITCODE` 확인 |
| `concurrency` / `timeout-minutes` / `permissions` | 동시 배포 시 이미지 태그 뒤섞임 방지, 러너 정지 시 무한 대기 방지, 기본 권한 축소 |
| 배포 전 테스트 | stg와 prod **양쪽 모두**에서 실행. stg를 거쳤다는 게 최신 커밋까지 통과했다는 보장은 아님 |
| `--no-deps` | 지정 서비스만 재기동. 의존 서비스(DB 등)가 불필요하게 재생성되지 않게 |
| 베이스 이미지 버전 고정 | node·nginx 태그를 정확한 버전으로 핀. `npm ci`(not `install`)로 lock 파일 고정 |
| 롤백 스크립트 | `rollback-production.ps1` — `:previous` 태그로 즉시 복원 |

**nginx 리버스 프록시 구조 (ARWS와 동일)**
브라우저는 프론트 컨테이너 **하나만** 봄. `/api/`는 nginx가 내부 도커 네트워크로 백엔드에 프록시 → **CORS 설정 자체가 불필요**하고 백엔드 포트가 외부에 노출되지 않음. SPA 라우팅은 `try_files ... /index.html` fallback.
`X-Forwarded-Proto`는 앞단 TLS 프록시가 설정한 값을 그대로 전달하고, 없을 때만 이 홉의 스킴으로 폴백 — 이걸 `$scheme`으로 덮어쓰면 prod에서 세션 쿠키에 Secure 플래그가 안 붙는 버그가 남(ARWS 실사례).

**BidRadar 고유 추가 항목** 수집기(collector)는 백엔드와 같은 이미지에 포함하되 별도 프로세스로 기동. **prod 서버가 작으므로 수집 동시성 상한을 환경변수로 두고 보수적으로 설정**한다(소스당 동시 요청 1개는 이미 설계안 04-4에 있음).

## 7. 확정 — 공고 심층 분석 기능 도입 (2026-08-31)

**결정** 사용자가 지정한 공고 한 건을 첨부 규격서까지 열어 정밀 분석하는 기능(S8)을 도입한다. 리포트 구성은 아래로 확정.

**입력 3경로** ① 목록에서 선택 ② URL·공고번호 직접 입력 ③ 규격서 파일 업로드(HWP·HWPX·PDF)

**리포트 8블록** 종합 판정 / 요약 타일 / **요구사양 ↔ 제품 대조표** / 경쟁 구도 / 레드플래그 조문 분석 / 참여 준비 체크리스트 / 일정 역산 / 분석 근거 문서

**출력** 화면 리포트 + DOCX·PDF 내보내기 + 공유 링크

**설계 원칙 3가지 (타협 불가)**

1. **충족 판정은 LLM이 하지 않는다.** LLM은 요구사양을 *추출·정규화*하고, 충족 여부는 **규칙(수치·집합 비교)**이 판정한다. 규칙으로 단정할 수 없으면 `확인 필요`로 두고 사람에게 넘긴다.
   → 근거: 과대판정은 곧 잘못된 참여 결정. `tests/test_match.py`가 과대판정 0건을 보증한다
2. **판정은 권고이지 결정이 아니다.** 모든 항목에 규격서 조문 위치를 붙인다. 근거를 못 대는 판정은 신뢰를 얻지 못한다
3. **자동 실행하지 않는다.** 첨부 규격서 파싱 + LLM 다단계로 건당 수십 초·비용이 발생. 사용자가 지정할 때만 실행하며, 동일 공고에 진행 중 작업이 있으면 중복 실행을 거부한다

**이 결정이 만든 선행 요구 2건**

- **제품 카탈로그(S9) 신설** — 대조표는 사내 제품 스펙·인증·실적이 구조화되어 있어야 성립. 카탈로그가 비면 대조표 전체가 `확인 필요`가 된다. 작업 순서상 U6(카탈로그)이 U9(분석)보다 앞
- **문서 추출 폴백 사슬** — 공공 규격서는 대부분 HWP이며 표·개체가 섞이면 추출 품질이 들쭉날쭉하다. `HWPX 직접 파싱 → HWP 파서 → LibreOffice 변환 → PDF 변환 → OCR → 사용자 붙여넣기` 다단 폴백으로 설계하고, **어느 단계에서 성공했는지 리포트에 남긴다.** 조용한 빈 결과를 금지

**Phase 0 필수 실측** 실제 나라장터 첨부 파일 20건으로 **추출 성공률을 측정**한다. 이 숫자가 S8 기능의 실현 가능성을 결정하므로, 측정 전에 S8 일정을 확정하지 않는다.

**SSRF 연결점** URL 직접 입력 경로는 소스 등록과 **동일한 `url_guard`를 통과**한다. 별도 경로를 만들지 않는다.

## 10. 확정 — S1 "트리아지"를 "분류 검수"로 재정의 (2026-09-01)

**결정** S1 화면의 핵심 가치를 "매일 참여여부를 훑어보는 트리아지"가 아니라 **"L1/L2-b/L3 분류 엔진의 정확도를 사람이 교정하는 분류 검수"**로 재정의한다.

**근거**
- 사용자가 지적한 핵심 문제: 고객마다 관심 분야가 다른데 어떻게 "고객별로" 검토 대상을 거르느냐 — 답은 **고객별이 아니라 카테고리(L2-b 대분류)별**로 작동한다는 것. 여러 고객이 같은 대분류를 공유하므로, 한 카테고리의 정확도를 튜닝하면 그 카테고리를 고른 **모든 고객이 동시에** 이득을 봄. 이 덕분에 고객 수가 늘어도 검토 부담이 비례해서 커지지 않음(카테고리 수 기준으로만 늘어남)
- "학습"은 ML 모델의 자동 학습이 아니라 **사람의 교정 기록을 근거로 L2-b 사전을 수동으로 고치는 것** — 설계안 06절의 기존 원칙("낙찰 데이터 1년 미만으로 모델을 학습시키려는 시도는 실패")과 일관성 유지
- 다만 "줄어든다"는 절반만 맞음: 튜닝될수록 **오탐(노이즈)은 줄지만, 진짜 관련 있는 후보 확인 자체는 계속 필요**하고, 소스·카테고리 범위가 넓어지면(8·9번 결정) 검토량이 다시 늘 수 있음
- **참여 여부 판단**(공고에 실제로 응찰할지)은 이 화면의 범위에서 제외 — 그립 자신의 사업적 결정이고, 향후 Premium 고객 대상 확장 가능성이 있으나 **S8 심층분석(요구사양 대조표 등) 완성 이후 별도로 재검토**하기로 함
- 남은 과제(v1 범위 밖): 그립 자신이 다루지 않는 카테고리(예: 에너지)를 원하는 외부 고객이 생기면, 내부 분류검수만으로는 그 카테고리의 튜닝 신호가 부족함 — 향후 **고객 자신의 피드백 루프**(예: 뉴스레터 항목별 "유용했나요?") 도입을 고려할 것

**영향** `docs/구현스펙.md` S1(공고 탐색·분류 검수), `classification_correction` 테이블 신설(08절). `docs/착수_체크리스트.md` 결정 #3(담당자 역할 재정의).

**추가 조사 결과 (2026-09-01)** 착수 전 3가지 법률·기술 조사를 진행함.

1. **공공데이터 재배포 적법성** — 공공데이터법 제3조④("공공기관은 ... 영리적 이용인 경우에도 이를 금지 또는 제한하여서는 아니 된다")에 따라 나라장터 데이터를 가공한 유료 뉴스레터는 **원칙적으로 합법**. 공공데이터포털 이용약관에도 재배포 금지 조항 없음. 단 데이터셋별 공공누리(KOGL) 라이선스 유형 확인 필요(제2·4유형은 상업 금지), 제3자 저작권 포함 정보(첨부 규격서 원문 등)는 별도 확인. 유사 선례로 G2BPlus 등이 이미 합법적으로 운영 중. **실무 조치**: 공공데이터포털 인증키 신청(착수_체크리스트 B-3) 시 활용목적에 "유료 구독형 뉴스레터"임을 명시할 것, 리포트에 데이터 출처 상시 표기.

2. **로그인 없는 익명 열람자 카운팅(공유 링크)** — 쿠키/로컬스토리지 기반 임의 식별자로 "몇 명 열람 추정"하는 방식은 한국법상 **저위험**. 한국은 EU와 달리 쿠키 전반에 사전동의(옵트인) 배너를 강제하지 않고, 광고 목적이 아닌 단순 통계 집계는 「온라인 맞춤형 광고 가이드라인」 적용 범위 밖으로 봄. 공유 링크가 **회사(구독) 단위 공용 링크**로 설계되어 개인 식별 소지가 더 낮음(법인은 개인정보보호법 보호 대상 아님). **실무 조치**: 개인정보처리방침에 쿠키 사용목적·거부방법·수집항목(IP·UA·접속시각) 명시, IP는 마스킹/해시 저장 권장, 발송 로그(수신자 이메일)와 열람 로그를 개인 단위로 결합 조회하는 기능은 만들지 않을 것(회사 단위 집계로만 유지).

3. **뉴스레터 발신 인프라** — 대표 발신주소는 `report@grib.co.kr`. 자동화 스크립트로 Hiworks SMTP를 통해 대량발송하는 것은 **Hiworks 이용약관 제29조 2항**("자체 제작 프로그램·자동화 스크립트를 통한 메일 대량발송" 금지) 위반 소지가 있고, 위반 시 발신 차단 사례가 실제 확인됨. 수신자가 전부 계약된 유료 고객이라 정보통신망법상 스팸(동의 없는 광고성 정보) 리스크는 낮지만, 이 약관 조항은 수신자 정당성과 무관하게 발신 "방식"(자동화·대량) 자체를 문제 삼음. 또한 도메인 평판을 사내 임직원 메일과 공유하므로, 뉴스레터가 스팸 신고를 받으면 사내 업무 메일 전달률도 같이 훼손될 수 있음.
   **결정**: 개발 단계에서는 **Hiworks SMTP로 진행**(구독자 규모가 작아 리스크가 낮은 지금 단계에서는 실용성 우선). 완화 조치로 (a) Hiworks 고객센터에 사전 문의/고지, (b) 발송을 한 번에 몰아보내지 않고 간격을 둠, (c) List-Unsubscribe 헤더·발신자 정보 명시, (d) 반송률·스팸신고율 모니터링. **서비스 정식 오픈 시점에 외부 ESP(Amazon SES·스티비 등) 전환 여부를 재결정**하기로 함 — 구독자 수가 늘어날수록(사업 성공 시나리오) 이 리스크가 커지므로, 그 시점 실제 규모를 보고 판단.

## 11. 확정 — 관심분야 리포트(카탈로그 없는 버전) 구현 방식 (2026-09-01)

**결정** "카탈로그 없이 관심 분야 선택에 의한 분석 결과 리포트부터 완료" 요청에 따라, S7 관심주제 매칭을 여러 건 모아 보여주는 **뉴스레터형 집계 리포트**를 구현. S8(개별 공고 심층분석)과는 다른 기능 — 8번 항목의 "남는 미정 사항(서명 링크 보안 모델)"을 이 범위에서 실무적으로 확정.

- **스냅샷 고정**: `newsletter_report`에 생성 시점의 매칭 결과(JSONB)를 그대로 저장. 이후 고객의 관심주제가 바뀌거나 공고가 갱신돼도 이미 발급된 리포트 내용은 바뀌지 않음 — "지난주에 보낸 링크를 다시 열었더니 내용이 달라져 있다"를 방지
- **토큰**: `secrets.token_urlsafe(24)`, 만료 없음(8번 결정 — 회사 단위로 계속 재열람), 1회성 아님

- **조회수는 근사 집계**(`view_count` 증가)일 뿐, 회사 단위 통계로만 남기고 개인 식별용으로 쓰지 않음(2번 항목과 일관)

## 12. 확정 — 로고 Target Lock (2026-09-01)

**결정** 4개 시안 중 조준경 형태의 "Target Lock" 채택. 동심원 2겹 + 십자 틱 4방향 + 중앙에서 벗어난 주황 블립. 정중앙이 아닌 위치가 "아직 조준 중"이라는 상태를 나타내며, 제품 정의(여러 신호 중 맞는 하나를 먼저 찾는다)와 맞는다.

**선정 근거** 시안 4종을 16px PNG로 실제 렌더해 판정. 조준 시안이 16px에서 가장 또렷했고, "신호 수신"과 "문서 스캔" 시안은 파비콘 크기에서 형태가 무너져 탈락(문서 시안은 접힌 모서리가 사라져 배터리로 읽힘).

**크기별 별도 파일** 완전형을 축소하면 내부 링과 블립이 뭉개지므로 3단계 분리. 48px+ mark.svg / 32~47px mark-32.svg / 16~31px favicon.svg. 마크를 24px 미만으로 축소해 쓰지 않는다.

**색** primary #DE5B21, 어두운 배경에서는 #FF9E6B. 워드마크는 Bid(잉크) + Radar(주황) 분리. **주황은 브랜드 색이지 도메인 색이 아니다** — 서비스가 특정 분야에 한정되지 않으므로, 화면에서 도메인을 구분하는 색은 도메인 데이터의 속성으로 관리하고 primary를 특정 도메인에 고정하지 않는다.

**이메일 제약** Gmail·Outlook은 SVG를 차단한다. 메일에는 PNG(@2x 포함)만 쓰고, 어두운 바(#161C24) 위 흰색 마크 조합을 표준으로 한다 — 수신자가 다크 모드로 열어도 동일하게 보이는 유일하게 안전한 방식. 흰 배경 + 검정 마크는 다크 모드에서 묻히므로 금지.

**산출물** brand/ 폴더 (SVG 7종, 파비콘 세트, 앱 아이콘, 락업·이메일 PNG, OG 이미지, Logo.tsx, 스니펫, 사용 가이드). 자산은 이미 완성되어 있으니 brand/ 안의 파일을 수정하지 말고 그대로 가져다 쓸 것.

- `app/collector/pii.py`의 `mask_pii()` — `raw_payload` 저장 직전(및 매핑 직전, 이중 방어)에 담당자 개인정보로 추정되는 키(`ofcl`/`manager`/`charger`/`picnm`/`pic_tel`/`email`/한글 등가어, 대소문자 무시)의 값을 재귀적으로 마스킹. 발주기관명류 키(`deptNm`/`orgNm`/`sorgnNm`/`ntceInsttNm`)는 허용목록으로 예외 처리

- **기존 데이터 감사 결과**: `raw_payload` 전 테이블·`notice` 테이블에서 개인정보로 추정되는 필드/패턴을 직접 조회했고(연락처 정규식·`manager`/`Ofcl`/`담당자` 등), **0건 검출**. 지금까지 실제로 라이브 수집된 소스는 IRIS(목록 응답 자체에 담당자 필드가 없음)뿐이라 별도 마스킹 마이그레이션은 작성하지 않았다 — 필요해지면(향후 새 소스가 담당자 필드를 실제로 내려줄 때) 그때 작성

## 19. 확정 — IRIS 실데이터 재수집(공고일 기준 2개월, 페이지네이션 도입) + 시드 데이터 정리 (2026-09-02)

**결정** 관리자 페이지 "공고 탐색"에 시드(데모) 공고와 실제 IRIS 공고가 소스 하나에 섞여 있던 문제를 발견 — IRIS 소스에 걸린 시드 공고 전량 삭제 후, 공고일 기준 **실제 2개월치**를 다시 수집했다. 이 과정에서 IRIS 수집이 실제로는 60일 캡이 아니라 "IRIS가 응답 1페이지에 보여주는 것"만 가져오고 있었다는 걸 발견해 페이지네이션을 추가했다.

**발견한 문제 2가지**
1. `_seed_notices()`가 소스를 무작위로 배정하다 보니, IRIS 소스에 실제 수집분(당시 10건)과 시드 더미 공고(16건)가 섞여 있었음 — 관리자가 "IRIS 실데이터"라고 믿고 볼 수 있는 화면이 아니었음.
2. IRIS `REAL_OPENAPI_CONFIG`엔 `date_range_params`가 없다(IRIS API 자체가 날짜범위 요청 파라미터를 안 받음) — 그래서 `_collection_window()`가 계산한 60일 캡이 실제로는 IRIS 호출에 전혀 반영되지 않고, `pageIndex=1` 고정이라 응답 1페이지(최신 10건)만 받고 있었다. "2개월치"라고 부르던 것의 실체는 "그 순간 1페이지에 있던 것"이었을 뿐.

**해결**
- `app/collector/adapters/openapi.py`에 `pagination` 설정(선택, `page_param`/`total_path`/`max_pages`)을 추가 — 응답의 `paginationInfo.totalPageCount`를 읽어 전 페이지를 순회한다. IRIS `REAL_OPENAPI_CONFIG`에 `"pagination": {"page_param": "pageIndex", "total_path": "$.paginationInfo.totalPageCount", "max_pages": 20}` 추가(`source_config` 새 버전 ver=2로 반영 — 기존 행 덮어쓰지 않음, CLAUDE.md 원칙).
- 날짜범위 파라미터가 없는 API는 서버가 기간을 안 걸러주므로, `app/collector/runner.py`의 `run_source()`가 매핑 후 `open_dt < begin`인 아이템을 걷어낸다(`out_of_window` 카운터로 결과에 노출 — 왜 몇 건이 빠졌는지 조용히 숨기지 않음).
- `python -m app.cli collect`에 `--force` 플래그 추가 — 관리자가 B등급 최소 수집 간격을 의도적으로 우회해 즉시 재수집할 때 씀(이번 재수집에 실제로 사용).
- IRIS 소스의 기존 notice 26건(시드 더미 16 + 실데이터 10) 전량 삭제(연결된 award 4건도 함께) 후, source_run 이력(데모 30일치 + 어제 실수집 1건)도 정리해 60일 캡이 온전히 적용되도록 하고 재수집.

**결과(2026-09-02 라이브 검증)** IRIS 접수예정 전체 16건 중 60일 이내 14건 수집(2026-07-10~2026-08-31), 2건(2026-06-10·2026-02-13)은 기간 밖으로 정상 제외. 이제 이 소스엔 시드 데이터가 전혀 없고 전부 실데이터다.

**영향** `app/collector/adapters/openapi.py`, `app/collector/runner.py`, `app/seed_constants.py`(IRIS config에 pagination 추가), `app/cli.py`(`--force` 플래그), `backend/tests/test_collector.py`(페이지네이션·기간필터 테스트 추가), `docs/설계안.md` Tier5, 운영 DB(시드 더미 삭제 + 실수집).

## 27. 확정 — 자동로그인을 is_dev(ENVIRONMENT)에서 분리, stg도 prod와 동일하게 로그인 절차 유지 (2026-09-03)

**결정** 로그인 화면 디버깅 중, 로컬 docker-compose(stg, 개발 PC에서 빌드+기동해 육안 확인하는 환경)에서 로그인 절차 없이 그냥 들어가진다는 걸 발견했다. 원인은 `/auth/dev-autologin` 라우트가 `settings.is_dev`(=`ENVIRONMENT != "production"`)로 게이팅돼 있었는데, stg도 `ENVIRONMENT` 기본값이 `"development"`라 자동로그인이 켜져 있었던 것 — stg는 원래 "prod에 배포하기 전 육안으로 확인"하는 용도(CLAUDE.md)인데, 로그인 자체를 건너뛰면 이번처럼 로그인 화면의 실제 버그(자동로그인 실패 시 안내 부재 등)를 stg 단계에서 못 잡고 지나칠 위험이 있었다.

**조치** 자동로그인 게이팅을 `is_dev`에서 분리해 별도 스위치 `settings.enable_dev_autologin`(기본 `False`)으로 바꿨다. 이제 stg·prod 모두 기본값으로는 자동로그인이 꺼져 있어 실제 로그인 절차를 거친다 — 필요하면(예: 재기동이 잦은 로컬 반복 개발 루프) 로컬 `.env`에 `ENABLE_DEV_AUTOLOGIN=true`를 직접 켜야 한다. 쿠키 `secure` 플래그는 여전히 `is_dev` 기반으로 유지 — TLS 유무에 따른 별개 관심사라 그대로 뒀다. `/api/health` 응답 필드도 `is_dev` → `dev_autologin_enabled`로 이름을 바꿔 용도를 명확히 했다(원래도 이 필드는 자동로그인 버튼 노출 여부 하나에만 쓰였음).

**영향** `backend/app/config.py`(`enable_dev_autologin` 추가), `backend/app/api/auth.py`·`backend/app/auth.py`(게이팅 변경), `backend/app/main.py`(`/api/health` 필드명 변경), `backend/tests/test_auth.py`(테스트를 `enable_dev_autologin` 기준으로 갱신, 기본 `False` 회귀 테스트 추가), `frontend/src/api/auth.ts`·`frontend/src/pages/LoginPage.tsx`(필드명 갱신).

## 28. 확정 — "로그인 상태 유지" 체크박스 (ARWS 패턴 이식) (2026-09-03)

**결정** 27번 항목에서 자동로그인을 껐더니 사용자가 "왜 자동로그인 선택 기능이 없냐"고 재질문 — 원하는 건 27번의 `ENABLE_DEV_AUTOLOGIN`(비밀번호 검증 자체를 건너뛰는 개발용 백도어)이 아니라, **최초엔 비밀번호로 로그인하되 이후엔 세션이 오래 유지되는** 기능이었다. ARWS(`backend/server.js`의 `remember` 파라미터, `admin-page-v2/sign-in-view.tsx`의 "로그인 상태 유지" 체크박스)에 이미 있는 패턴을 그대로 이식했다 — 비밀번호는 정상적으로 검증하고, 체크박스 선택 시에만 세션 수명을 12시간(`SESSION_TTL`)에서 30일(`REMEMBER_SESSION_TTL`)로 늘린다.

**둘의 구분을 명확히 유지**: `ENABLE_DEV_AUTOLOGIN`(27번)은 비밀번호 없이 즉시 로그인 — prod에서 사용자가 선택 가능하게 열면 단일 공유 계정 인증 자체가 무력화되므로 절대 사용자 선택 기능으로 노출하지 않는다. 이번 "로그인 상태 유지"는 비밀번호 검증을 그대로 거치는 세션 수명 연장일 뿐이라 stg·prod 모두 안전하게 사용자에게 노출한다.

**구현 시 주의점** 쿠키의 `max_age`와 서버 세션(`auth_session.expires_at`)의 TTL이 반드시 같이 움직여야 한다 — 하나만 늘리면(예: 쿠키만 30일로 늘리고 서버 세션은 그대로 12시간) 쿠키는 남아있는데 서버가 401을 내는 불일치가 생긴다. `_set_session_cookie`가 `remember` 플래그를 직접 받아 `REMEMBER_SESSION_TTL`/`SESSION_TTL` 중 하나를 골라 두 값에 동시에 적용하도록 정리했다.

**영향** `backend/app/auth.py`(`REMEMBER_SESSION_TTL` 추가, `authenticate()`가 `remember` 인자 받음), `backend/app/api/auth.py`(`LoginRequest.remember`, `_set_session_cookie`가 TTL 결정), `backend/tests/test_auth.py`(12시간/30일 세션 만료시각 회귀 테스트 추가), `frontend/src/api/auth.ts`·`frontend/src/pages/LoginPage.tsx`(체크박스 UI, ARWS와 동일 라벨 "로그인 상태 유지").

## 31. 확정/발견 — K-water 입찰공고 실등록 완료, 중부발전(SRM 로그인 게이트)·한전 API(별도 포털 필요) 보류 (2026-09-03)

**K-water 입찰공고 — 등록 완료, 라이브 검증 성공**
- 상세 URL 패턴: `https://ebid.kwater.or.kr/fz?bidno={공고번호}` — 구글에 색인된 실제 사례(페이지 제목이 "입찰공고상세 [공고번호]"로 정확히 매칭)로 발견, 직접 호출해 302 리다이렉트 확인.

**한국중부발전 — 이중 blocker 확인**
1. 사용자가 직접 발견: 중부발전 입찰공고가 **`srm.kepco.net`**(한전+발전자회사 공동 전자조달)으로 연결됨. 이 시스템은 **인증서 로그인 + ActiveX 확장(INIS_EX.exe) 설치가 있어야 상세 내용을 볼 수 있음** — URL 패턴을 찾아도 우리 사용자가 로그인 없이는 못 본다는 점에서, 단순 "URL 필드 없음"보다 근본적인 문제.
2. 공식 API(`apis.data.go.kr/B552521/cbid/getData`)를 실키로 직접 호출해도 `resultCode: 02 데이터베이스 에러입니다`만 돌아옴 — 파라미터 문제인지 서비스 자체 문제인지 이번엔 원인을 못 찾음.

## 33. 확정 — 공고 생명주기 상태(입찰미정→입찰예정→입찰접수→입찰마감) 도입 (2026-09-03)

**결정** IRIS 접수예정 공고를 실사이트와 대조하다가(32번 항목 직후) 발견한 문제 — 우리 소스명은 "IRIS 접수예정"인데 실제로는 이미 "접수중"인 공고가 섞여 있었다. 데이터 자체(`extra.rcveSttSeNmLst`)는 정확했지만, 소스명이 실제 상태를 대표하지 못해 오해 소지가 있었다. 사용자가 이를 계기로 "공고 항목이 생명주기를 가져야 하는 것 아니냐"는 설계를 제안 — `notice.stage`(어느 수집 단계/소스에서 왔는가, 고정값)와는 별개로, **`open_dt`/`close_dt`와 현재 시각만으로 조회할 때마다 다시 계산하는 4단계 상태**를 도입했다:

1. **입찰미정** — 시작일 자체가 아직 미확정(`open_dt` 없음)
2. **입찰예정** — 시작일은 있으나 아직 도래 안 함
3. **입찰접수** — 시작일이 지났고 마감 전(마감일이 없으면 계속 이 상태)
4. **입찰마감** — 마감일이 지남

이름은 사용자가 처음 제안한 "입찰공개→입찰예정→입찰접수→입찰마감"에서 "입찰공개"만 "입찰미정"으로 조정했다(1번 상태의 핵심은 "날짜가 아직 안 정해짐"이지 "공개 여부"가 아니라서 — "공개"는 한국 공공조달 맥락에서 보통 정보/문서 공개를 가리키는 말이라 의미가 어긋남).

**핵심 설계 원칙**: 소스가 주는 원본 상태 문자열(IRIS의 `rcveSttSeNmLst`, 나라장터의 상태 코드 등)을 참조하지 않고 **우리 필드(open_dt/close_dt)만으로 독립적으로 계산**한다 — 사용자가 직접 확인 질문("API에서 얻어오는 상태 정보를 쓰는 게 아니라 우리 시스템에서 관리하는 형태냐")으로 명확히 한 지점. 이렇게 하면 (1) 소스마다 제각각인 상태 어휘에 의존하지 않고 전 소스에 동일하게 적용되고, (2) DB에 저장하지 않고 매번 재계산하므로 시간이 지나며 실제와 어긋나는(stale) 문제가 구조적으로 안 생긴다. 원본 상태 문자열은 버리지 않고 `notice.extra`에 그대로 남아 참고용으로 보인다.

**영향** `app/services/notice_query.py`(`compute_bid_status()`, `BID_STATUSES`), `app/services/notice_detail.py`(상세 조회에도 적용), `backend/tests/test_notices.py`(4단계 전부 + 방어적 케이스 회귀 테스트), `frontend/src/api/notices.ts`(`BidStatus` 타입·`BID_STATUS_LABELS`), `frontend/src/components/NoticeCard.tsx`(기존 D-day 전용 칩을 이 상태 칩으로 통합 대체), `frontend/src/pages/NoticeDetailPage.tsx`(상세 페이지에도 상태 칩 추가).

**조사 결과** 나라장터(g2b.go.kr)는 WebSquare 완전 SPA라 정적 스크래핑 불가 — 상세 웹페이지 원문을 가져오려면 헤드리스 브라우저(Playwright)가 필요함을 확인(에이전트 조사 + WebFetch로 직접 재현: `www.g2b.go.kr` 최상위 도메인과 상세페이지(`/link/.../single/`) 둘 다 `sso.g2b.go.kr` 로그인으로 302 리다이렉트됨을 확인). **Playwright 도입을 사용자가 승인**(별도 작업으로 진행, 이번 항목엔 미포함) — 로그인 게이트가 WebFetch 특유의 요청 방식 때문인지, 실제 익명 방문자도 겪는 진짜 제약인지는 Playwright로 직접 떠봐야 확정됨. 사전규격 상세 URL 패턴은 API 응답에 없고 이번 조사로도 못 찾아, 나라장터 사전규격정보서비스 등록은 K-water 2종과 같은 이유로 계속 보류.

**나라장터 첨부문서는 로그인 없이 다운로드 가능함을 확인** — 상세 *페이지*(`/link/PNPE027_01/single/`)는 위 로그인 게이트에 걸리지만, 첨부파일 *다운로드* 경로(`/pn/pnp/pnpe/UntyAtchFile/downloadFile.do`)는 완전히 별개 엔드포인트라 로그인 없이 200으로 실제 파일이 그대로 내려온다(실제 나라장터 공고 첨부 HWP를 직접 다운로드해 검증). 상세 웹페이지 원문(Playwright 필요)과 첨부문서(지금 바로 가능)는 서로 다른 두 갈래임 — 첨부문서 쪽은 이번에 바로 진행.

IRIS는 반대로 서버렌더링 정적 HTML이라 문제없고, 상세페이지 "■ 공고문" 섹션에 공고 전문이 그대로 있음을 확인(에이전트 조사) — 첨부문서가 구버전 HWP라 반쪽만 추출되는 경우의 우회로로 유용, 다음 작업으로 연결 예정.

**버그 3건 발견·수정**
1. **IRIS 접수예정이 처음부터 "접수중"만 가져오고 있었음** — advisory INBOX #3 원안 의도("접수중·마감은 범위 아님")대로면 POST 바디에 `ancmPrg=ancmPre`를 보내야 하는데 이 키 자체가 빠져 있어 서버 히든필드 기본값(ancmIng=접수중)으로 응답해왔다. 실제 탭 전환 스크립트(`f_bsnsAncmListForm_go`)가 쓰는 값(ancmPre/ancmIng/ancmEnd)을 확인해 수정, 정렬은 등록일 내림차순이라 IRIS 공모예고와 달리 전량 스캔 불필요(max_pages=15로 유지).
2. **나라장터 입찰공고정보서비스(용역) 날짜 포맷이 실제 응답과 안 맞아 전량 조용히 skipped** — format_hint가 `%Y%m%d%H%M`인데 실제 응답은 `2026-09-01 03:00:32`(대시·콜론 포함). open_dt가 매퍼 필수필드라 파싱 실패 시 항목 자체가 통째로 버려짐(DB에 나라장터 공고 0건으로 확인). 서비스키 승인이 이번에 처음 나서 발견이 늦었음. 3종(용역/물품/공사) 전부 올바른 포맷으로 수정.
3. **페이지네이션 부재로 100건 초과분 누락** — 나라장터 응답은 페이지당 최대 100건 고정인데 pagination 설정이 없어 1페이지만 가져왔음(발주계획(용역) 60일치 실측 338건 중 100건만 저장됨을 확인). 입찰공고 3종은 추가로 **60일 범위 요청 시 "입력범위값 초과 에러"**(resultCode 07)까지 확인 — 30일이 상한이라 `max_lookback_days: 30` 지정. 전부 pagination(빈 페이지에서 멈추는 방식, max_pages=50) 추가.

**HWP 전문 추출 — LibreOffice 시도 후 폐기, pyhwp로 교체** 처음엔 LibreOffice headless 변환을 붙였으나(`soffice --convert-to pdf`), 실제 나라장터 첨부 HWP로 검증하니 "source file could not be loaded"로 전부 실패. 원인 확인: 이 프로젝트가 쓰는 LibreOffice 7.4 빌드엔 `writer_MIZI_Hwp_97`(1990년대 구버전 "한글 97" 전용 필터)만 등록돼 있고, 요즘 정부 사이트 HWP(HWP5, 한글 2007 이후)를 여는 필터가 아예 없다(한국어 언어팩 추가 설치로도 해결 안 됨, HWPX도 동일하게 실패 확인) — 즉 설정 문제가 아니라 이 배포판 자체의 한계. 사용자가 한컴 공식 "HWPX 변환기"를 제안했으나 이건 실제 한컴오피스가 설치된 Windows PC(.NET 4.8 등)가 필요한 GUI 도구라 Docker Linux 백엔드엔 적용 불가 — 대신 `pyhwp`(HWP5 바이너리 레코드를 직접 파싱하는 순수 파이썬 라이브러리, `hwp5txt` CLI 제공)로 교체, 나라장터 실제 첨부 HWP로 전문 추출 성공 확인(61KB 파일 → 3,688자, 표 포함). LibreOffice는 Dockerfile에서 완전히 제거.

**나라장터 첨부문서 파이프라인 연결 완료** `app/services/analysis_pilot.py`를 IRIS 전용에서 IRIS+나라장터 2군 지원으로 확장. 나라장터는 상세페이지 HTML을 아예 안 연다 — 목록 API 응답(수집 시 이미 저장된 raw_payload)에 첨부 다운로드 URL(ntceSpecDocUrl1~10)이 직접 들어있어, notice_no(bidNtceNo)로 raw_payload에서 항목을 다시 찾아 바로 다운로드한다. 첨부 **다운로드**(별도 엔드포인트 `/pn/pnp/pnpe/UntyAtchFile/downloadFile.do`)는 로그인 없이 가능함을 실제 파일로 확인 — 상세 **페이지**(`/link/.../single/`, WebSquare SPA)만 로그인 게이트(WebFetch로 직접 재현: `sso.g2b.go.kr`로 302)에 걸린다는 걸 이번에 명확히 구분했다. 발주계획현황서비스는 API 응답에 첨부 URL 필드 자체가 없어(atchFileExistnceYn 전부 "N") 이 경로로는 0건 — Playwright 이후 과제로 유지.

## 37. 확정 — 공고 마감 보존 정책(수집 시 제외 + 30일 후 삭제), 정렬 페이지네이션 안정성 버그 수정 (2026-09-04)

**결정**
1. 수집 단계에서 이미 마감된(`close_dt` < 지금) 항목은 애초에 저장하지 않는다. `close_dt`가 없는 소스(IRIS 등)는 판단 근거가 없으므로 대상 아님.

3. 기존에 쌓여있던 마감 공고 4,101건을 즉시 삭제(retention-days=0으로 1회 실행) — 36번의 "그대로 유지" 방침을 대체.

**부수 발견 — 정렬 페이지네이션 불안정** 나라장터 대량 수집(약 2만 건 규모)으로 `close_dt`·`priority`가 동일한 행이 흔해지면서, `app/services/notice_query.py`의 5개 정렬 옵션 전부에 동점 처리 기준(`notice.id`)이 없어 같은 공고가 서로 다른 페이지에 겹쳐 나타나는 문제를 실측으로 발견 — 전부 `notice.id`를 마지막 정렬 기준으로 추가해 수정. 시드 데이터(120건) 규모에서는 동점이 드물어 안 드러났던 버그.

## 41. 확정 — 로그인 "상태 유지" 체크박스 방식으로 복귀(36번 변경), 소스별 첨부문서 자동 분석 토글 도입 (2026-09-05)

## 47. 확정 — 공고 탐색 "소스" 필터를 "데이터 소스"(공고기관 단위)로 재구성, 카드에 채널·단계 통합 표시, 세로형 과제내용 전체 표시 (2026-09-05)

**배경** 사용자 요청 3건: (1) 세로형 카드에서 과제내용이 잘리는 문제, (2) 공고 탐색의 "소스" 필터를 "데이터 소스"로 개명하고 개별 소스 행이 아니라 나라장터·IRIS 같은 공고기관 단위로 묶기, (3) 카드 제목 위 타원형(칩) 텍스트에 공고기관명과 단계(사전규격/발주계획/입찰공고 등)를 함께 표시.

**"소스"가 세분화돼 있던 문제** `source` 테이블은 물품/용역/공사, 서비스 종류별로 쪼개져 있어(나라장터만 10개 행 — 사전규격 3종·발주계획 3종·입찰공고 3종·낙찰정보 1종) 기존 필터가 이 15개 행을 그대로 드롭다운에 노출했다. `source.org_name`("이 소스를 운영하는 기관")도 그룹핑에 못 쓴다 — 나라장터 계열 10개 전부 org_name이 "조달청"이라 사용자가 인지하는 "나라장터"라는 채널명과 다르기 때문(반대로 IRIS는 org_name 자체가 "IRIS"라 소스마다 의미가 일관되지 않음).

**결정** `source.channel_name`(신규 컬럼) — 사용자에게 보이는 포털 브랜드명("나라장터"/"IRIS"/"K-water"/"과학기술정보통신부"). `app/services/source_registry.py`의 `derive_channel_name()`이 소스명 접두어로 판별해 시드 시점에 채운다(매칭 실패 시 org_name으로 폴백 — 조용히 사라지지 않게). 기존 15개 행은 마이그레이션의 SQL `CASE`로 일괄 백필.

`filter_options()`의 `sources: [{id,name}]`를 `channels: [{name, source_ids}]`로 교체 — 프론트는 채널 단위로 선택하고, 내부적으로는 여전히 `source_ids` 배열을 백엔드에 보낸다(필터링 쿼리 자체는 변경 없음, `notice.source_id IN (...)`). 공고 목록 조회에도 `source` 조인을 추가해 `channel_name`을 얹었고, `NoticeCard`가 기존 "단계" 칩을 "나라장터 · 입찰공고"처럼 채널+단계 통합 표기로 바꿨다.

**세로형 과제내용** 가로형은 3줄 클램프를 유지하되(공간이 넓어 대부분 다 보임), 세로형은 클램프를 없애 전체를 표시하도록 수정 — 카드 높이가 CSS grid의 행 단위로 맞춰지므로 긴 카드가 있는 행은 자동으로 늘어나고 짧은 카드는 그 높이에 맞춰 늘어난다(레이아웃 깨짐 없음, `flexGrow` 스페이서로 액션 버튼은 항상 카드 하단에 고정).

**영향** `backend/migrations/versions/b2c3d4e5f6a7_source_channel_name.py`(신규), `backend/app/models/sources.py`, `backend/app/services/source_registry.py`(`derive_channel_name` 신설), `backend/app/seed_data.py`, `backend/app/services/notice_query.py`, `backend/tests/test_notices.py`·`test_runner.py`, `frontend/src/api/notices.ts`, `frontend/src/components/NoticeFilterBar.tsx`, `frontend/src/components/NoticeCard.tsx`.
