## 00. 요약

결론부터 — **입찰공고를 모니터링하면 이미 늦습니다.** 실제 승부는 그보다 앞선 두 단계에서 갈립니다.

### 핵심 판단 4가지

**1. 감시 대상은 '입찰공고'가 아니라 '사전규격공개'다.**
사전규격 단계에서 규격 의견을 제출하면 사양에 우리 제품 특성을 반영시킬 여지가 생깁니다. 공고가 뜬 뒤에는 사양이 이미 고정되어 있습니다. 나라장터는 사전규격을 별도 OpenAPI로 개방하고 있으므로, **같은 파이프라인에서 무료로 얻을 수 있는 리드타임**입니다.

**2. 커버리지 공백은 '자체조달 기관'과 '학교장터'에 있다.**
나라장터 API만으로는 LH·한전·코레일·도로공사 등 자체 전자조달 운영기관과, 스마트교육 물품의 실질 창구인 학교장터(S2B)가 통째로 빠집니다. 이 두 축은 별도 수집 경로가 필요합니다.

**3. 진짜 자산은 '낙찰 이력'이다.**
낙찰정보 API를 함께 축적하면 기관별 단가 수준, 경쟁사 수주 패턴, 반복 발주 주기가 데이터로 남습니다. 유료 입찰정보 서비스가 팔지 않는, 우리만의 영업 자산이 됩니다.

**4. 소스는 코드가 아니라 데이터여야 한다. *(v0.2 추가)***
발주 채널은 계속 늘어납니다. 새 기관을 추가할 때마다 개발자가 코드를 고치고 배포해야 한다면, 시스템은 6개월 뒤 낡습니다. **관리자가 화면에서 직접 소스를 등록**할 수 있게 만들되, 임의 URL 수집은 보안·법적 리스크를 동반하므로 안전장치를 함께 설계합니다. → **04절**

### 권장 접근

**단계적 구축.** 1주차에 3개월치 과거 데이터를 백필해 "우리 도메인에 실제로 연 몇 건, 얼마 규모의 발주가 있는가"를 먼저 실측하고, 그 숫자를 보고 나머지 투자 규모를 결정합니다.

- 총 예상 공수: **백엔드 1명 × 8~10주 + 프론트 0.5명 × 4주** *(소스 레지스트리 반영해 v0.1 대비 상향)*
- 외부 비용: 사실상 서버비뿐 (나라장터 OpenAPI 무료)

## 01. 문제 정의와 성공 기준

### 현재 방식의 3가지 손실

| 손실 | 내용 |
|---|---|
| **인지 지연** | 나라장터 수기 검색은 주 단위 주기가 한계. 공고 기간이 짧은 건(긴급공고·재공고)은 발견 시점에 이미 준비 시간이 없음 |
| **탐색 누락** | "산업안전"이라는 단어로 공고가 올라오는 경우는 드묾. 실제 공고명은 `지능형 CCTV 구축`, `안전관리 통합관제시스템`, `스마트 안전 IoT 센서 설치`처럼 흩어져 있고 발주기관마다 용어가 다름. 사람의 키워드 검색은 이 분산을 못 따라감 |
| **판단 근거 부재** | 발견해도 "들어갈 만한가"를 판단할 근거(과거 낙찰가·경쟁 구도·반복 발주 패턴)가 없어 감으로 결정 |

### 성공 기준 (구축 후 3개월 측정)

| 지표 | 정의 | 목표 |
|---|---|---|
| **인지 리드타임** | 공고 게시 → 내부 인지까지 경과 시간 | 24시간 이내 (사전규격은 게시 당일) |
| **커버리지** | 사후 수동 점검으로 찾은 유효 공고 중 시스템이 잡아낸 비율 | ≥ 95% |
| **정밀도** | 알림된 건 중 담당자가 "검토 가치 있음"으로 판정한 비율 | ≥ 60% |
| **사전규격 대응 건수** | 사전규격 단계에서 의견 제출 또는 사전 접촉한 건 | 분기당 3건 이상 |
| **소스 자립도** *(v0.2)* | 신규 소스 등록 중 **개발자 개입 없이** 관리자가 끝낸 비율 | ≥ 70% |

> 정밀도 60%는 의도적으로 낮게 잡은 값입니다. **놓치는 것(누락)이 헛수고(오탐)보다 훨씬 비싸므로** 초기에는 재현율 우선으로 튜닝합니다.

> **배경**: 유료 뉴스레터 서비스(의사결정_로그 8번)는 산업안전·스마트교육에 갇히지 않고 고객이 선택한 임의 주제를 다뤄야 함(광범위 주제 전제). 사용자가 나라장터(G2B)와 함께 **IRIS(국가연구개발사업 통합정보시스템, iris.go.kr)**를 "가장 중요한 사이트 2곳" 중 하나로 지목해 심층 조사함.

**⚠️ 중요 정정**: IRIS는 **국가연구개발사업(R&D 과제공모)에만 한정**되고 일반 용역·물품·공사 **입찰(조달)은 포함하지 않음**. BidRadar 핵심 도메인(CCTV·안전장비·스마트교실 구매 등)은 R&D보다 구매성 입찰 비중이 크므로, **IRIS는 Tier1(나라장터)의 대체재가 아니라 R&D 채널 보완재**임.

**IRIS 자체 — 수집 경로 확정(2026-09-01, U11 실연동 완료)**: 전용 OpenAPI·RSS는 없다. 다만 **비공식이지만 실제로 동작하는 JSON 엔드포인트를 찾아 직접 검증했고, U11 파이프라인에 실연동해 실 데이터 10건을 라이브로 수집·저장하는 데 성공했다**(서비스키 불필요, 로그인 불필요).

- **최종 확정 엔드포인트**: `POST https://www.iris.go.kr/contents/retrieveBsnsAncmBtinSituList.do` — 폼바디로 `pageIndex` 등 필터 파라미터를 보내면 `{"listBsnsAncmBtinSitu": [...], "paginationInfo": {...}}` 형태의 순수 JSON이 돌아온다. 이 경로 하나로 **34개 부처 × 42개 전문기관 전체**가 나온다 — 특정 전문기관을 거칠 필요가 없다.
- **여기 도달하기까지 두 번 정정이 있었다** — 이 경위 자체가 기록해둘 가치가 있다:
  1. 처음엔 `POST retrieveBsnsAncmBtinSituListView.do`(끝에 "View"가 붙음)를 시도했는데, 세션 쿠키·Referer·브라우저 헤더를 다 갖춰도 매번 빈 HTML 셸 페이지만 돌아왔다(WAF로 추정)
  2. 이 URL을 **GET으로 열면 실제 데이터가 나온다**는 조사 결과를 전달받았으나, 직접 GET으로 재현한 결과 **역시 빈 템플릿(jsrender `{{:ancmId}}` 같은 미치환 플레이스홀더)만 돌아옴** — 이 페이지는 서버렌더링이 아니라 로드 후 별도 AJAX로 채워지는 구조였음
  3. 그 페이지가 실제로 호출하는 JS(`bsnsAncmBtinSituList.js`)를 열어 진짜 대상을 확인한 결과, **"View"가 빠진 `retrieveBsnsAncmBtinSituList.do`**(위 확정 엔드포인트)가 진짜였다 — 여기에 POST하니 바로 JSON이 나옴

|---|---|---|
| **L0** 스케줄러 | 폴링 주기 관리 | 소스별 주기 분리 — 사전규격·입찰공고 **1시간 간격(평일 08–20시)**, 낙찰·계약 **1일 1회**, 발주계획·예산 **주 1회**. 주기는 하드코딩이 아니라 **소스 레코드의 속성**(04절). 실시간 스트리밍은 원본 시스템이 지원하지 않으므로 무의미 |
| **L1** 수집기 | **범용 어댑터 + 소스 설정** | ⭐ **v0.2 변경** — 기관별 전용 코드가 아니라 `openapi / rss / html` **3종 범용 어댑터**가 소스 레코드의 설정을 읽어 동작. 신규 소스는 코드 배포 없이 레코드 추가로 붙음 (04절) |
| **L2** 원본 적재 | Raw 보존 | 응답 JSON/HTML을 **가공 없이 그대로** 보존. 필터 규칙은 계속 바뀌므로 원본을 남겨야 규칙 변경 시 재처리 가능. 안 해두면 6개월 뒤 키워드 고칠 때마다 API를 다시 긁어야 함 |
| **L3** 정규화 | 필드 매핑·중복제거 | 소스별 상이 필드를 **매핑 정의**(04절)에 따라 공통 스키마로 변환. 자연키 = `소스코드 + 공고번호 + 차수`. 공고번호가 없는 소스는 `소스코드 + URL 해시`로 대체. 정정·재공고는 **동일 공고의 버전**으로 묶어 알림 중복 차단 |
| **L4** 분류·스코어링 | 05·06절 로직 | 결과를 `score`, `domain`, `reason`(판정 근거 텍스트)로 저장. **근거를 함께 저장해야** 담당자가 왜 이게 떴는지 알고 규칙을 고칠 수 있음 |
| **L5** 대시보드 | 표출 | 웹 대시보드가 기본 인터페이스. 마감 임박·고득점 신규 건은 별도 강조 (Slack·메일은 추후 확장 가능, 이번 범위 제외) |

### ⚠️ 먼저 확인할 제약 — API 트래픽 한도

공공데이터포털 **개발계정은 일 1,000건**으로 제한되며, 운영계정은 활용사례 등록 후 증량 신청이 가능합니다.

> 서비스 6종 × 업무구분 4종 × 시간당 1회 × 12시간 = **개발계정 한도 초과**

**Phase 0에서 운영계정 전환과 트래픽 증량을 먼저 신청**해야 하며, 승인에 시간이 걸리므로 **착수 첫날 처리할 항목**입니다.

### 기술 스택 (권장)

| 영역 | 선택 | 근거 |
|---|---|---|
| 수집·처리 | Python (requests + BeautifulSoup/lxml + pandas) | 3종 범용 어댑터를 동일 인터페이스로 구현 |
| 저장 | PostgreSQL 단일 인스턴스 | 연간 수만 건 규모로 별도 검색엔진 불필요. 한국어 검색은 `pg_trgm` 인덱스로 충분. 소스 설정은 `jsonb` 컬럼으로 유연하게 |
| 스케줄 | cron 또는 APScheduler | Airflow는 이 규모에 과함 |
| 대시보드 | 사내 기존 스택에 맞춤 | 없다면 FastAPI + 정적 프론트가 가장 저렴 |

## 04. 소스 레지스트리 — 관리자 직접 등록 ⭐ *v0.2 신설*

> **요구사항:** 관리자가 개발자 도움 없이 새 입찰 사이트를 시스템에 추가할 수 있어야 한다.

### 04-1. 설계 원칙

**소스를 코드가 아니라 데이터로 다룹니다.** 기관마다 전용 수집기를 짜는 대신, **3종 범용 어댑터**가 DB의 소스 레코드를 읽어 동작하는 구조입니다.

| 어댑터 타입 | 대상 | 관리자 난이도 | 안정성 |
|---|---|---|---|
| **`openapi`** | 공공데이터포털 계열 REST API | **매우 쉬움** — 데이터셋 ID/오퍼레이션명/인증키만 입력 | 높음 |
| **`feed`** | RSS / Atom / 사이트맵 | **쉬움** — URL만 입력하면 대부분 자동 |
| **`html`** | 임의 목록 페이지 | **어려움** — 필드별 선택자 지정 필요, 자동 제안 보조 | 낮음 (사이트 개편에 취약) |

> **⚠️ 솔직한 한계 —** "URL만 넣으면 알아서 되는" 수준은 `openapi`와 `feed`에서만 성립합니다. `html` 타입은 자동 제안이 초안을 만들어주더라도 **관리자의 확인·수정이 사실상 필수**이며, 로그인이 필요하거나 JavaScript로 목록을 그리는 사이트는 이 기능으로 감당되지 않습니다. 그런 사이트는 예외 처리로 개발 요청 대기열에 넘기는 UX가 정직합니다.

### 04-2. 등록 마법사 (5단계)

```
[1] 기본 정보        [2] 자동 탐지        [3] 필드 매핑        [4] 시험 수집        [5] 검토·활성화
 이름 · 기관 · URL  →  타입 판별          →  선택자/경로 확인  →  최근 20건 미리보기 →  준법 확인 후 승인
 도메인 · 수집주기      robots.txt 확인       자동 제안 + 수정      정규화 결과 검증      감사 로그 기록
```

**[1] 기본 정보** — 소스명, 발주기관, 시작 URL, 대상 도메인(산업안전/스마트교육/공통), 수집 단계(사전규격/입찰공고/낙찰), 수집 주기.

**[2] 자동 탐지 (probe)** — 시스템이 URL을 한 번 호출해 다음을 판정합니다.
- 응답이 JSON인가 → `openapi` 후보. `apis.data.go.kr` 도메인이면 **공공데이터포털 프리셋** 자동 적용
- `<link rel="alternate" type="application/rss+xml">` 존재 → `feed` 후보
- 그 외 HTML → `html` 후보. 반복 구조(테이블 행, 리스트 아이템) 후보를 추출
- **robots.txt 확인 결과와 응답 헤더를 화면에 그대로 표시** — 관리자가 보고 판단할 수 있게

**[3] 필드 매핑** — 우리 공통 스키마의 필드에 소스의 무엇을 연결할지 지정합니다.

| 공통 필드 | 필수 | `openapi` 매핑 예 | `html` 매핑 예 |
|---|---|---|---|
| `title` 공고명 | ✅ | `$.response.body.items[*].bidNtceNm` | `td.subject > a` |
| `notice_no` 공고번호 | — | `$..bidNtceNo` | `td.no` |
| `org_name` 발주기관 | ✅ | `$..ntceInsttNm` | `td.org` |
| `open_dt` 게시일 | ✅ | `$..bidNtceDt` | `td.date` |
| `close_dt` 마감일 | — | `$..bidClseDt` | `td.deadline` |
| `est_price` 추정가격 | — | `$..presmptPrce` | `td.price` |
| `url` 원문 링크 | ✅ | `$..bidNtceDtlUrl` | `td.subject > a[href]` |

- **자동 제안**: 샘플 응답을 LLM에 넘겨 매핑 초안을 생성 → 관리자가 확인·수정. 관리자가 JSONPath나 CSS 선택자를 처음부터 쓰게 하지 않습니다.
- **날짜 형식·통화 단위**는 소스마다 다르므로 파서 형식(`YYYY-MM-DD`, `YYYYMMDDHHmm`, 천 단위 콤마 등)을 함께 지정합니다.
- **필수 4개 필드(`title`·`org_name`·`open_dt`·`url`)가 매핑되지 않으면 다음 단계로 못 넘어갑니다.**

**[4] 시험 수집 (dry run)** — 실제로 최근 20건을 가져와 **원본 값 ↔ 정규화 값을 나란히** 보여줍니다. 여기서 날짜가 깨지거나 제목이 빈 값으로 나오면 [3]으로 돌아갑니다. **저장은 하지 않습니다.**

**[5] 검토·활성화** — 아래 준법 확인을 통과해야 활성화됩니다.

### 04-3. 준법 게이트 (활성화 전 필수)

| 항목 | 처리 |
|---|---|
| **robots.txt** | 시스템이 자동 확인. **차단 경로면 활성화 거부** (관리자가 우회할 수 없게 — 이건 옵션이 아님) |
| **이용약관 확인** | "해당 사이트의 이용약관을 확인했으며 수집이 금지되지 않음을 확인한다"는 명시적 체크. **체크한 계정과 시각이 감사 로그에 기록됨** — 책임 소재를 남기는 것이 목적 |
| **요청 간격 하한** | 최소 간격을 시스템이 강제(기본 60분, 하한 10분). 관리자가 이보다 짧게 설정 불가 |
| **User-Agent** | 회사명과 연락처를 담은 고정 UA 사용. 익명 수집 금지 — 문제가 생기면 상대 기관이 우리에게 연락할 수 있어야 함 |
| **로그인 필요 사이트** | **이 기능으로 등록 불가.** 계정 공유·자동 로그인은 약관 위반 소지가 크므로 개발팀 검토 대기열로 이관 |

### 04-4. 보안 — 임의 URL 입력의 위험 ⚠️

**관리자에게 "아무 URL이나 넣으면 서버가 호출한다"는 기능을 주는 순간, 서버는 공격자의 대리인이 될 수 있습니다(SSRF).** 관리자를 못 믿어서가 아니라, 계정 탈취 한 번이 내부망 전체 노출로 번지기 때문입니다. 아래는 타협 불가 항목입니다.

| 위협 | 대응 |
|---|---|
| **SSRF — 내부망 접근** | 도메인 리졸브 후 **IP 대역 차단목록** 강제: `127.0.0.0/8`, `10/8`, `172.16/12`, `192.168/16`, `169.254.169.254`(클라우드 메타데이터), `::1`, 링크로컬 전체. **호스트명이 아니라 실제 리졸브된 IP를 검사** |
| **DNS rebinding** | 리졸브한 IP를 고정해 그 IP로 직접 연결(Host 헤더 유지). 리졸브 시점과 연결 시점 사이에 IP가 바뀌는 공격 차단 |
| **리다이렉트 우회** | 리다이렉트 **매 홉마다 IP 재검증**. 최대 홉 수 3회 제한 |
| **프로토콜 악용** | `http`/`https`만 허용. `file://`, `gopher://`, `ftp://` 등 전면 차단 |
| **자원 고갈** | 응답 크기 상한(예: 10MB), 타임아웃(예: 20초), 소스당 동시 요청 1개 |
| **저장 자격증명 유출** | API 키는 **암호화 저장**, 화면에는 마스킹 표시, 감사 로그에 평문 기록 금지 |
| **권한 오남용** | 소스 등록·수정·삭제는 **관리자 역할 전용**. 일반 사용자는 조회만. 모든 변경은 `누가·언제·무엇을` 감사 로그에 기록 |
| **HTML 파싱 취약점** | 파서는 스크립트를 실행하지 않는 정적 파서(lxml/BeautifulSoup) 사용. 헤드리스 브라우저가 필요한 소스는 별도 격리 환경으로 분리하고 이 기능 범위에서 제외 |

> **이 절은 "나중에"가 없습니다.** 소스 등록 기능을 켜는 릴리스에 SSRF 방어가 함께 들어가야 합니다. 기능만 먼저 열고 방어를 다음 스프린트로 미루면, 그 사이가 정확히 사고 구간입니다.

### 04-5. 소스 건전성 모니터링

**셀렉터 기반 소스는 사이트가 개편되면 조용히 죽습니다.** 에러도 안 나고, 그냥 0건이 수집됩니다. 담당자는 "요즘 그 기관 공고가 없네"라고 생각하고 몇 달을 흘려보냅니다. **이 기능의 최대 함정이며, 자동 감지 없이는 반드시 발생합니다.**

| 상태 | 판정 기준 | 조치 |
|---|---|---|
| 🟢 **정상** | 최근 수집 건수가 과거 평균 범위 내 | — |
| 🟡 **주의** | 필수 필드 결측률 > 20%, 또는 수집량이 평균의 30% 이하 | 대시보드 배지 표시 |
| 🔴 **실패** | **연속 3회 0건**, 또는 HTTP 오류 연속 3회, 또는 스키마 드리프트 감지 | 소스 관리 화면 상단 경보 + 담당자 배정 |
| ⚫ **비활성** | 관리자가 수동 중지, 또는 실패 상태 14일 경과 시 자동 중지 | 재등록 마법사로 유도 |

- **스키마 드리프트 감지** — 매핑된 선택자/경로가 응답에서 사라지면 즉시 실패 처리. "결과가 0건"과 "선택자가 안 맞음"을 구분해서 알려줘야 관리자가 뭘 고쳐야 할지 압니다.
- **소스별 최근 30일 수집량 스파크라인**을 소스 목록에 표시 — 눈으로 이상을 잡을 수 있게.

### 04-6. 버전 관리와 롤백

소스 설정은 **변경할 때마다 새 버전으로 기록**합니다. 관리자가 매핑을 고치다 망가뜨렸을 때 되돌릴 수 있어야 하고, "언제부터 이 소스의 데이터 품질이 떨어졌나"를 추적할 수 있어야 합니다.

- 수집된 각 공고 레코드에 **당시 소스 설정 버전(`source_ver`)을 기록**
- 소스 상세 화면에서 이전 버전으로 **1클릭 롤백**
- 시스템 소스(나라장터 등 코드로 관리되는 핵심 소스)는 **삭제 불가 · 비활성화만 가능**. 관리자가 실수로 나라장터를 지우는 사고를 구조적으로 막습니다

### 04-7. 소스 삭제 정책

소스를 지워도 **이미 수집된 공고는 지우지 않습니다.** 과거 데이터가 낙찰 분석·시장 분석의 근거이기 때문입니다. 삭제는 "더 이상 수집하지 않음 + 목록에서 숨김"이며, 수집된 공고에는 `출처 소스 삭제됨` 표시가 붙습니다.

## 05. 분류 · 필터링 알고리즘

키워드 매칭만으로는 오탐이 폭증하고, LLM 전량 판정은 비용이 폭증합니다. **저비용 필터로 후보를 좁힌 뒤 고비용 판정을 붙이는 3단 구조**로 갑니다.

### L1 — 하드 필터 (규칙 기반, 비용 0)

구조화 필드로 명백한 무관 건을 먼저 제거. **통과율 목표 5~10%.**

- **세부품명번호** — 물품 공고는 품명번호가 부여됨. 영상감시장치 계열 품명번호 집합을 사전으로 구축해 1차 통과. 사전은 조달청 상품정보시스템 등록 물품 파일데이터(`15050862`)에서 자동 생성하되, **대표 품명번호는 Phase 0에서 실데이터로 확정** ⚠️
- **업종코드** — 정보통신공사업, 소프트웨어사업 등 참여 가능 업종으로 제한. 코드값은 조달청 코드 목록으로 확정 ⚠️
- **기관 화이트리스트** — 교육청·KERIS 등 스마트교육 도메인은 기관 코드만으로 통과
- **추정가격 하한** — 소액 건(예: 3천만 원 미만)은 별도 저우선 큐로 분리. 완전히 버리지 않는 이유는 소액 반복 발주가 레퍼런스 확보에 유효하기 때문
- ⚠️ **주의 1: 용역·공사 공고에는 품명번호가 없습니다.** 이 경우 업종코드와 공고명 키워드에만 의존하므로, 품명번호 필터를 전체에 강제 적용하면 **대형 SI 건을 통째로 놓칩니다.**
- ⚠️ **주의 2: 관리자가 추가한 소스는 품명번호·업종코드가 없는 경우가 대부분입니다.** 이런 소스는 L1을 **자동 통과**시키고 L2 키워드부터 적용해야 합니다. 그렇지 않으면 새로 붙인 소스가 전량 걸러져 "추가했는데 아무것도 안 뜬다"가 됩니다. — 소스 레코드에 `skip_l1` 플래그로 제어

### L2 — 가중 키워드 스코어링

공고명 + 규격서 본문에 도메인별 사전으로 점수 부여. 사전은 **운영하며 계속 자라는 자산**이므로 코드가 아니라 DB 테이블로 관리하고 담당자가 대시보드에서 직접 추가할 수 있게 합니다.

| 구분 | 가중 | 산업안전 도메인 | 스마트교육 도메인 |
|---|---|---|---|
| **핵심어** `core` | **+3** | 지능형 CCTV, 영상관제, 영상분석, 안전관리시스템, 통합관제센터, 스마트 안전, 산업안전, 중대재해, 위험구역, 침입감지, AI 영상, 객체인식, 이상행동 감지 | 스마트교실, 전자칠판, 디지털교과서, 미래교실, 학습지원 플랫폼, AI 디지털교과서, 스마트단말, 수업지원 SW |
| **기술어** `tech` | **+2** | IoT 센서, 무선센서, 가스감지, 열화상, 라이다, 순찰로봇, 무인이동체, 드론, 엣지 AI, 영상저장장치, NVR, 관제 플랫폼 | 전자교탁, 미러링, 화면공유, 무선 AP, 태블릿 관리, MDM, 디지털 사이니지, UHD 디스플레이 |
| **맥락어** `ctx` | **+1** | 구축, 고도화, 확충, 개선, 실증, 시범사업, 스마트팩토리, 스마트건설, 스마트시티 | 구축, 보급, 교체, 노후, 환경개선, 그린스마트 |
| **제외어** `block` | **−5** | 임대, 렌탈, 이전설치, 단순 유지보수, 소모품, 철거, 렌즈 교체, 저장매체 구매 | 급식, 통학차량, 교복, 도서 구입, 청소용역 |

> **합계 ≥ 4 이면 L3로 승급.** 제외어를 강한 음수로 두어 "CCTV 임대", "관제실 청소용역" 같은 전형적 오탐을 확실히 눌러줍니다.
> 위 사전은 **출발점**이며, Phase 0의 3개월 백필로 실제 공고명 분포를 본 뒤 확정합니다.

### L2-b — 고객 대면 산업/기술 분류 체계 *2026-09-01 추가 (유료 서비스 전제)*

> **문제**: 유료 뉴스레터는 고객이 관심 분야를 직접 선택해야 하는데(의사결정_로그 8번 Standard), 정부 공식 분류체계를 그대로 쓰기엔 부적합함을 조사로 확인함 — 조달청 세부품명번호는 "구매 물품" 단위 코드로 항목 수가 방대(공개 미기재)하고, 국가과학기술표준분류체계("6T")는 대분류 22개·중분류 약 277개·**소분류 약 2,800개**로 R&D 과제 코드 부여용이라 고객이 훑어볼 수 있는 규모가 아니며 5년 주기 개정이라 최신 기술 반영이 느림. 한국표준산업분류(KSIC, 대분류21·세세분류1196개)는 업종 통계 목적이라 기술 트렌드와 애초에 무관함.
>
> **선례**: 정부 스스로도 표준분류를 실무에 그대로 안 쓰고 간소화된 목록을 별도로 만듦 — **12대 국가전략기술**(대분류 12개+세부 핵심기술 50개, 2023년 국가전략기술육성 특별법 기반)과 **통계청 산업 특수분류**(로봇산업·스마트제조기술산업·디지털산업 등 신산업마다 KSIC와 별개로 만든 수십 개 규모 미니 목록, 약 37종 운영 중)가 근거.

**해결책 — 3계층 하이브리드 분류**

| 계층 | 내용 | 규모 |
|---|---|---|
| **1. 고객 대면 대분류** | BidRadar가 직접 큐레이션한 업종·기술 카테고리. 정부 코드를 그대로 쓰지 않고 고객이 실제 쓰는 언어로 설계 | 15~25개 (12대 국가전략기술 규모가 상한 기준) |
| **2. 자유 키워드 태그** | S7(관심 주제) 화면의 태그 칩 추가/삭제로 이미 설계됨. **최신기술(생성형AI·디지털트윈 등)은 여기서 흡수** — 대분류 개정 없이 즉시 반영 가능 | 자유 입력, 계속 성장 |
| **3. 내부 매핑 테이블(비공개)** | 1·2계층 각 항목을 조달청 세부품명번호·과학기술표준분류 코드에 백엔드에서 연결. 고객에게 노출 안 함, L1 하드필터 정확도 강화용 | L1 사전(위 세부품명번호 사전)의 확장판 |

**대분류 초안(15~25개, 검토 필요)**: 산업안전/CCTV·영상보안 · 스마트제조/팩토리 · 로봇/자동화 · IoT/센서 · AI/데이터 · 스마트교육/에듀테크 · 에너지/신재생·ESS · 환경/탄소중립 · 헬스케어/바이오·의료기기 · 모빌리티/자율주행 · 반도체/디스플레이 · 스마트시티/인프라관제 · 국방/보안 · 콘텐츠/미디어/XR · 물류/스마트항만 · 농수산/스마트팜 · 통신/5G·6G · 우주/항공 · 관광 · 핀테크/금융보안

**운영 원칙**: 대분류·매핑 테이블은 L2 사전과 동일하게 **코드가 아니라 DB 테이블**로 관리(살아있는 자산). 분기별로 고객이 추가한 신규 키워드 클러스터를 검토해 대분류 승격 여부를 판단.

### L3 — LLM 판정 및 요약 (L2 통과분에만)

규격서 본문·첨부 텍스트를 LLM에 넘겨 구조화 출력을 받습니다. 일 수십 건 수준이므로 비용은 무시 가능합니다.

- **도메인 판정** — 산업안전 / 스마트교육 / 무관 (+ 확신도)
- **3줄 요약** — 무엇을, 어디에, 왜 발주하는가
- **참여 자격 추출** — 실적 요건, 인증 요건(GS인증·CC인증·조달우수제품 등), 지역제한, 중소기업 간 경쟁 여부
  → **실무에서 가장 큰 시간 절약 지점.** 사람이 규격서 수십 장을 읽어야 알 수 있는 정보
- **레드플래그** — 특정 업체 사양으로 의심되는 조항(특정 모델 스펙 나열, 과도한 실적 요건) 탐지

> **설계 원칙 —** 모든 판정 결과에 **근거 텍스트를 함께 저장**합니다. "왜 이 공고가 떴는지" 담당자가 즉시 확인할 수 있어야 규칙을 개선할 수 있고, 그 개선 루프가 없으면 시스템은 3개월 안에 신뢰를 잃고 아무도 안 봅니다.

## 06. 수주 우선순위 스코어링

"관련 있는 공고"를 찾는 것과 "우리가 딸 수 있는 공고"를 찾는 것은 다른 문제입니다. **후자가 이 시스템의 차별점입니다.**

```
우선순위 = 적합도 × 규모계수 × 승산계수 × 시급도

  적합도   (0~1)    L2 점수 + L3 확신도. 제품/역량 매칭
  규모계수 (0.5~2)  log(추정가격) 정규화. 큰 건에 가중
  승산계수 (0~1.5)  아래 신호들의 가중합  ← 핵심
  시급도   (0.5~2)  마감까지 남은 일수의 역수. 임박 건 상단 고정
```

### 승산계수를 구성하는 신호

| 신호 | 출처 | 해석 |
|---|---|---|
| **사전규격 참여 여부** | 사전규격 API | 우리가 규격 의견을 낸 건은 승산이 유의하게 높음. **가장 강한 양의 신호** |
| **기관 거래 이력** | 내부 CRM + 계약정보 API | 기존 납품 기관의 재발주·증설 건 |
| **경쟁 집중도** | 낙찰정보 API 누적 | 동일 기관·동일 품목에서 특정 업체가 반복 낙찰 → 진입 난도 높음. **음의 신호** |
| **자격 요건 충족도** | L3 추출 결과 | 실적·인증 요건 충족 여부. **미충족이면 아무리 좋은 건이어도 0에 가깝게 눌러야 함** |
| **레드플래그** | L3 판정 | 특정 업체 맞춤 사양 의심 건은 감점. 단, 완전 배제하지 않고 별도 표시 — 이의 제기 판단은 사람이 함 |
| **계약 만료 예측** | 계약정보 API | 계약기간이 끝나가는 건은 재발주 후보. **공고 전에 영업할 수 있는 유일한 정량 신호** |

> 초기 가중치는 전문가 판단으로 손으로 정합니다. 낙찰 데이터가 **1년 이상** 쌓인 뒤에야 회귀로 보정할 의미가 생기며, 그 전에 모델을 학습시키려는 시도는 데이터 부족으로 실패합니다.

## 10. 구축 로드맵

**Phase 0의 결과를 보고 Phase 2 이후 투자를 결정하는 구조**로 설계했습니다. 시장이 생각보다 작다면 거기서 멈추면 됩니다.

### Phase 0 — 타당성 실측 · 1주 · 공수 0.5인

- 공공데이터포털 인증키 발급 및 **운영계정 트래픽 증량 신청** (승인 지연 대비, 착수 첫날 처리)
- 최근 3~6개월 나라장터 공고 전량 백필 (일회성 스크립트)
- 실제 공고명 분포 확인 → 품명번호·업종코드·키워드 사전 **확정**
- 자체조달 26개 기관 전수 조사 → API 유무 및 우선순위 판정
- **산출물: "우리 도메인 연간 발주 건수 / 총 금액 / 상위 발주기관 20곳" 실측 보고**

### Phase 1 — 수집 파이프라인 · 최소 화면 · 3주 · 백엔드 1인

- ⭐ **처음부터 소스 레지스트리 구조로 구현** — 나라장터도 "하드코딩된 수집기"가 아니라 **`openapi` 어댑터 + 소스 레코드**로 붙입니다. 관리자 UI는 아직 없어도, **데이터 구조와 어댑터 추상화는 여기서 잡아야 합니다.** 나중에 갈아엎으면 Phase 2가 2배로 늘어납니다
- 나라장터 6개 서비스 수집기 + 원본 적재 + 정규화
- L1·L2 필터, L3 LLM 판정 연결
- Screen 1(오늘의 신규) 단일 화면 — **여기서부터 실사용 시작**
- **병행: 담당자 1인이 2주간 매일 트리아지**하며 오탐 사례 수집 → 사전 튜닝

### Phase 2 — 소스 레지스트리 UI · 커버리지 확장 · 4주 · 백엔드 1인 + 프론트 0.5인

- ⭐ **04절 소스 레지스트리 전체** — 등록 마법사, 준법 게이트, **SSRF 방어(같은 릴리스 필수)**, 건전성 모니터링, 버전 관리
- ⭐ Screen 5(소스 관리) 구현
- K-water·방사청 API를 **관리자 UI로 직접 등록해 기능 검증** — 개발자가 코드로 붙이지 말고, 실제로 화면에서 등록되는지가 이 기능의 인수 조건
- LH·코레일·학교장터 `html` 소스 등록 (약관 검토 후)
- Screen 2~4 구현, 키워드 사전 편집 UI

### Phase 3 — 승산 모델 · 영업 자산화 · 상시 · 공수 0.3인

- 낙찰 데이터 누적 → 승산계수 보정
- 계약 만료 예측 기반 **선제 영업 알림**
- Tier 4 선행 신호(예산·KOSHA 품목등록·혁신제품) 연동
- 사업계획 수립용 시장 분석 리포트 자동 생성

## 12. 결정 요청

Phase 0 착수 전에 확정이 필요한 4가지입니다.

**Q1. 산업안전 도메인의 사업 범위를 어디까지로 볼 것인가**
제조 현장(스마트팩토리 안전) / 건설 현장(스마트건설 안전) / 공공 시설물(터널·댐·역사 관제) / 도시 방범(지자체 CCTV 통합관제) — 이 넷은 발주기관도 사양도 경쟁 구도도 전혀 다릅니다. 전부 담으면 필터가 흐려집니다. **우선 2개로 좁히기를 권합니다.**

**Q2. 직접 수주형인가, 협력사 납품형인가**
대형 SI 원청으로 들어갈 건과, SI 업체에 제품을 납품할 건은 모니터링 대상이 다릅니다. 후자라면 **낙찰정보 API로 SI 업체의 수주 현황을 추적**하는 것이 공고 자체를 보는 것보다 유효합니다. 이 판단에 따라 05·06절 설계가 달라집니다.

**Q3. 일일 트리아지 담당자를 누구로 할 것인가**
이 시스템의 성패는 기술이 아니라 **매일 15분을 쓰는 사람이 있는가**에 달려 있습니다. Phase 1 시작 전에 담당자와 백업 1인이 지정되어야 하며, **지정되지 않으면 구축을 시작하지 않기를 권합니다.**

**Q4. 소스 등록 기능의 대상 관리자를 누구로 볼 것인가** ⭐ *v0.2 추가*
이 답에 따라 04-2 마법사의 UX 깊이가 달라집니다.

- **(a) 비개발 실무자** — CSS 선택자를 절대 못 쓴다고 가정. 자동 제안 품질에 투자하고, `html` 타입은 "화면에서 클릭으로 필드 지정" 수준까지 만들어야 함. **개발 공수 +2주**
- **(b) 사내 개발자/기획자** — JSONPath·선택자를 직접 입력 가능. 마법사는 가볍게, 대신 **소스 건전성 모니터링과 롤백에 투자**. 04절 설계는 이쪽을 기본 가정으로 작성했습니다

> 권장은 **(b)로 시작**입니다. 대부분의 소스는 `openapi`·`feed` 타입이라 (b) 수준이면 충분하고, 어려운 `html` 소스는 어차피 개발자 판단이 필요합니다. (a)는 실사용 데이터를 본 뒤 Phase 3에서 검토해도 늦지 않습니다.
