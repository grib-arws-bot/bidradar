## 0. 배경 — 왜 지금 이 문서가 필요한가

- 서버가 2코어/3.8GB/57GB → **4코어/8GB/120GB로 증설됨**(2026-09-09). ARWS는 주로 야간(새벽
  파이프라인), BidRadar는 주로 주간에 도는 걸 감안해 한 서버를 같이 쓰기로 함.
- BidRadar `docs/의사결정_로그.md` 6번(2026-08-31)에 이미 "ARWS의 infra/·
  scripts/deploy-to-production.ps1·.github/workflows/ 구조를 그대로 복제한다", "prod 서버
  사양이 작음을 전제로 설계"라고 명시돼 있음 — 이 문서는 그 결정을 실제로 구현할 때 ARWS
  쪽에 이미 있는 실물 파일들이 정확히 어디에 있는지, 무엇을 그대로 베끼고 무엇을 BidRadar
  사정에 맞게 바꿔야 하는지를 정리한 것.
- 확인 시점(2026-09-09) 기준 BidRadar에는 `docker-compose.prod.yml`/배포 스크립트/
  `.github/workflows/`가 전혀 없음(stg만 존재) — 이번이 첫 prod 셋업.

## 1. 서버 쪽 현재 상태 (ARWS 세션이 확인·준비한 것)

- `~/bidradar` 빈 디렉토리를 서버에 미리 만들어둠(`~/arws`와 동급 — 최초 배포 시 이 자리에
  git clone).
- Docker compose project명 충돌 걱정 없음 — BidRadar `infra/docker-compose.yml`에 이미
  `name: bidradar`가 명시돼 있어(2026-09-01 사고 재발방지 조치) ARWS(`infra` project)와
  별도 네트워크로 자동 분리됨. **추가 조치 불필요.**
- 리소스: ARWS/BidRadar 사용 시간대가 겹치지 않는다고 보고, 코어/메모리 하드 파티셔닝은
  하지 않을 계획(제안) — 대신 BidRadar 쪽 prod compose에 안전장치용 `mem_limit` 정도만
  걸어두는 걸 권장(구체적 수치는 아래 6절).

## 2. ⚠️ 막힌 것 — 외부 접속용 신규 포트 (Jeffrey 확인 필요)

ARWS는 자체서명 TLS 종료 프록시(`infra/tls-proxy/`)가 기존 NAT 규칙(9993→3200, 9995→15900)을
그대로 받아써서 별도 포트 요청 없이 해결했음(`infra/DEPLOYMENT.md`, 의사결정_로그 참고).
BidRadar는 **완전히 새로운 서비스**라 기존 NAT 규칙을 재사용할 수 없음 — 서버 관리자에게
**신규 외부 포트 1개**(BidRadar 프런트엔드용, ARWS의 3200 역할) 요청이 필요함. 백엔드를
브라우저가 직접 호출하지 않는 구조(로컬 compose의 `nginx.conf`가 `/api`를 프록시하는 것으로
보임 — 8절 "미확인" 참고)라면 프런트엔드용 1개만으로 충분할 가능성이 큼, ARWS의 15900(n8n
직접 접속용) 같은 두 번째 포트가 정말 필요한지는 BidRadar 쪽에서 판단.

→ 포트 값이 정해지면 이 문서와 실제 `docker-compose.prod.yml`의 `tls-proxy` 서비스에
반영할 것.

## 3. docker-compose.prod.yml 패턴

참고 원본: `D:\Code-CLI\ARWS\infra\docker-compose.prod.yml`, `infra/tls-proxy/nginx.conf`,
`infra/tls-proxy/gen-cert.sh`, `infra/tls-proxy/certs/`.

핵심 아이디어: base `docker-compose.yml`의 서비스들은 prod에서 호스트 포트를 전부 없애고
(`ports: !override []` — 그냥 `[]`만 쓰면 병합돼서 안 지워짐, 반드시 `!override` 필요,
ARWS가 2026-08-11에 실제로 겪은 함정), 신규 `tls-proxy` 서비스 하나가 새 NAT 포트를 받아
자체서명 인증서로 TLS를 종료한 � 평문 HTTP로 frontend/backend에 넘김.

```yaml
services:
  db:
    ports: !override []
  backend:
    ports: !override []
  frontend:
    ports: !override []

  tls-proxy:
    image: nginx:1.31.3-alpine   # ARWS가 실측 확인한 버전, :alpine(무버전) 태그는 피할 것
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-sk", "-o", "/dev/null", "-f", "https://localhost:<신규포트>/"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
    ports:
      - "<신규포트>:<신규포트>"
    volumes:
      - ./tls-proxy/nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - ./tls-proxy/certs:/etc/nginx/certs:ro
    depends_on:
      - frontend
```

`nginx.conf`는 ARWS 것을 거의 그대로 베껴도 됨 — `resolver 127.0.0.11 valid=10s;` +
`proxy_pass`에 변수 쓰기(컨테이너 기동 초기 DNS 실패로 크래시 루프 나는 함정 회피, ARWS가
2026-08-11에 실제로 겪음) 부분이 핵심. 인증서는 `gen-cert.sh` 그대로 복제해 최초 1회 생성.

## 4. 배포 스크립트 패턴

참고 원본: `D:\Code-CLI\ARWS\scripts\deploy-to-production.ps1`,
`D:\Code-CLI\ARWS\scripts\rollback-production.ps1`.

ARWS 스크립트가 n8n/Baserow(공식 이미지, 이 스크립트 대상 아님) 관련 로직을 빼면 거의 그대로
재사용 가능한 구조:

1. 사전점검 — 로컬 HEAD == origin/main, 워킹트리 clean 아니면 중단
2. 로컬에서 backend/frontend 이미지 빌드(**서버에서 빌드 금지** — BidRadar 자신의
   의사결정_로그 6번에도 이미 이 이유가 적혀 있음)
3. 이미지에 git commit sha 태그(`:latest`와 별도 보관, 롤백용)
4. `docker save` → tar.gz → `scp`로 서버 전송
5. 서버 git 체크아웃(`~/bidradar`)을 origin/main으로 `git fetch && git merge --ff-only` —
   compose 파일처럼 이미지에 안 담기는 설정 반영
6. 로컬 `.env` vs 서버 `.env` 변수명 비교 경고(서버 `.env`는 수동 관리이므로)
7. 서버: 교체 전 이미지를 `:previous`로 백업 → `docker load` → `docker compose -f
   docker-compose.yml -f docker-compose.prod.yml up -d`(`--build` 없이)
8. 로컬 임시파일 정리
9. 배포 확인 — HTTP 응답 + 로그인 스모크 테스트(200뿐 아니라 실제 로그인 성공까지)

**ARWS가 실제로 겪고 고친 함정들(그대로 반영 권장)**:
- PowerShell `$ErrorActionPreference="Stop"`은 docker/ssh/scp/git 같은 네이티브 명령의
  비정상 종료코드를 못 잡음 — 매 명령 뒤 `$LASTEXITCODE` 확인 필요.
- 배포 스크립트가 도중 실패해도(예: git merge 실패) 이미 서버로 전송된 tar.gz를 정리 안
  하면 디스크에 계속 쌓임 — 업로드 완료 이후의 모든 실패 경로에서 정리하도록 설계할 것
  (ARWS도 2026-09-08에 이 문제를 겪고 고침, `scripts/deploy-to-production.ps1`의
  `$script:tarUploaded` 플래그 부분 참고).
- 로컬 HEAD와 origin/main이 다르면 "이미지=로컬 코드 / 서버 설정=origin/main / 기록된
  sha=서버에 없는 커밋"이라는 3중 불일치가 생길 수 있어 빌드 전에 미리 확인해서 막음.

## 5. GitHub Actions 패턴

참고 원본: `D:\Code-CLI\ARWS\.github\workflows\deploy-stg.yml`,
`D:\Code-CLI\ARWS\.github\workflows\deploy-prod.yml`(정확한 파일명은 로컬에서 재확인 필요 —
7절 미확인 항목).

- `workflow_dispatch`만 — 자동 트리거 없음, "사람이 버튼을 눌러야 prod로 넘어간다"를
  private 저장소에서 유료 Required reviewers 없이 대체하는 방법.
- self-hosted 러너 사용(BidRadar도 같은 개발 PC에서 실행) — **미확인**: ARWS 러너를 그대로
  공유할지, BidRadar용을 별도 등록할지는 이 세션이 판단할 수 없음(GitHub Actions 러너 설정은
  ARWS 저장소 밖의 계정/머신 레벨 설정이라 BidRadar 쪽에서 직접 확인 필요).
- `workflow_dispatch`는 임의 브랜치 지정이 가능하므로, 체크아웃 전에 ref가 main인지 확인해
  아니면 즉시 실패시키는 가드 필요(self-hosted 러너에 실 시크릿이 있으므로).
- 러너가 `_work` 디렉토리를 재사용하는 경우 복사해둔 `.env`가 다음 실행에 남을 수 있어
  `if: always()`로 마지막에 삭제.

## 6. 백업 + 리소스 안전장치

- ARWS `infra/backup-baserow.sh`(pg_dump -Fc 커스텀 포맷, 단일 파일 통짜 덤프 — 배치
  분할 방식은 복원 시 시퀀스 중복 에러를 겪은 전례가 있어 피함)를 참고해 BidRadar 자체
  Postgres 백업 스크립트 신설 권장. 저장 위치는 `~/arws-backups`와 섞이지 않게
  `~/bidradar-backups`(또는 `~/backups/bidradar/`) 제안. 보관기간은 ARWS와 동일한 이유
  (사내 전용, 장기보관 불필요)로 짧게(3일 정도) 권장하되 BidRadar 데이터 특성(공공입찰
  데이터 재수집 가능 여부 등)에 따라 조정 여지 있음 — 이 판단은 BidRadar 쪽 몫.
- 메모리: db+backend+frontend 합산 `mem_limit` 대략 2GB 내외 권장(정확한 수치는 실측 후
  조정 — 이 세션은 BidRadar 실제 메모리 사용량을 측정한 적 없어 추정치임, 8절 참고).
  ARWS/BidRadar 사용 시간대가 겹치지 않는다고 보고 코어는 하드 제한하지 않는 걸 제안하지만,
  겹치는 시간대가 실제로 있다면 재검토 필요.

## 7. 이번 계획과 별개로 진행 중인 것

같은 시점에 ARWS 쪽 admin-page-v2에 "서버 관리" 페이지를 신설해 ARWS+BidRadar 컨테이너
상태를 통합해서 보는 기능을 준비 중(Jeffrey 요청). 이건 ARWS 저장소에서 구현하고, BidRadar
쪽에서 별도로 준비할 건 없음 — 컨테이너 이름이 `bidradar-` 접두로 시작한다는 점만 이 기능이
그대로 활용함(이미 `name: bidradar`로 보장됨).

## 8. 조사 한계 (미확인 항목)

- BidRadar backend가 정확히 어떤 프레임워크인지(FastAPI 추정 — `docker-compose.yml`의
  헬스체크가 `urllib.request.urlopen`을 쓰는 걸로 봐서 순수 Python이지 uvicorn 여부 등은
  `backend/` 코드를 직접 안 열어봐서 미확인).
- `.github/workflows/` 자체가 아직 없어(확인 시점 기준) ARWS 쪽 정확한 파일명·세부 설정을
  참고용으로만 적었음 — 실제 작성 시 `D:\Code-CLI\ARWS\.github\workflows\`를 직접 열어
  최신 버전으로 재확인할 것.
- self-hosted 러너를 ARWS와 공유할지 별도 등록할지는 GitHub Actions/머신 설정 영역이라
  이 문서로 결정할 수 없음.
- BidRadar 실제 운영 시 메모리/CPU 사용량 실측치 없음(아직 stg에서만 돌아봤을 것으로 추정) —
  6절의 `mem_limit` 권장치는 추정.
- 외부 접속용 신규 포트 번호(2절) — 서버 관리자 확인 전이라 미정.
